# 公司 UI 共性规则

## 基准与实现归属

- 当前核对 IHOS／海蓝、PURE／天蓝两个评审基准。风格族与配色分别识别；PURE 天蓝不等同于 IHOS 的天蓝变体。
- 业务结构、操作表达、组件选型、表单排布、弹窗尺寸和动态适配默认共用；主题条件只承载确证差异。同一业务代码分别记录两基准结果，归类方法见[风格差异](../references/style-differences.md#按对象语义判断共性)。
- 优先复用目标工程组件库与公共能力；规范描述目标表现，框架适配负责 API、生命周期和代码。HISUI 工程由 HISUI 管已有控件视觉与状态，页面只补业务容器缺口。
- 模块内共用样式在已授权需求范围内处理；跨模块或全局公共样式的新增、调整，先交用户审核具体缺口、影响与拟改内容。

## 读取和应用

- 按 [skill 路由](../skills/imedical-ui/SKILL.md)只读当前场景的参考。每项要求保留原有“必须／默认／建议／可选”强度及其场景、状态和例外。
- [来源](../references/source-catalog.md)区分明确文字、构件图形参数、页面示例、设计器操作。设计器编辑指令不进入产品行为；示例字段、宽度、页码和数量不成为业务默认。
- 采用图形参数前确认测量对象、描边、盒模型及导出倍数；先核对原生控件的实际效果，再决定局部实现，避免直接将画板矩形尺寸覆盖到框架控件。
- 将材料推广为公司通用规范，需要两风格证据或明确跨风格条款；单方示例保留来源范围。这项证据要求不缩小当前业务实现范围：只有 PURE 截图也应先判断业务共性，而非自动限定为 PURE。来源冲突保留双方出处，定向核对。
- 规范涉及必填、默认值、权限、编辑路径或流程行为时，对照业务契约登记差异；UI 任务不自动改变持久化值、事件、请求参数或业务决定。

## 核查与交付

- 按本次改动选择宽度、控件状态和动态阶段，检查布局关系、内容可达及目标主题；使用现有验证协议与任务记录，不复制验收状态机。
- 报告共性改动、分别适用的差异及出处；技术自测、真实页面验证和用户 UI 评审分别记录。两基准有缺口时保留未测/待确认状态。
