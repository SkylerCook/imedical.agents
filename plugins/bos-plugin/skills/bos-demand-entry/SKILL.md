# 标版需求录入与提交衔接

帮助请求（`--help`、查看用法）：先读取[统一帮助协议](../../../../docs/guides/capability-help.md)，按当前定义展示帮助后结束；Overlay 未映射 `docs/` 时先按 `.agents/capability.json` 的 `CapabilityRoot` 定位协议；附带执行参数也不进入业务流程。

用于 `standard` 需求文本：从代码改动或指定提交补录，或根据用户主题及可选资料向本组/其他组提需求；显式 `--work` 则整理工作记录。三类来源共用需求整理、文本/草稿、可选 Excel 和编号回填，只有代码来源按需衔接提交。用户说“根据提交提需求”“代码改完补需求”“提需求给某组”“按这个主题/资料生成需求”时使用。此入口明确选择 standard，不修改工程默认交付类型；明确 project 交付请求转交原流程。

默认输出可复制文本；`--excel` 与 `--Excel` 等价，额外生成 29 列导入表，不是必经步骤。Excel 缺少模块编码时先交付文本，再一次性请求缺失字段；不猜测编号、模块编码、指派人或验收完成事实。只按用户明确需要生成 Excel，不因闭环请求自动导出。

文本、Excel 和编号回填均为本地流程，不要求 BOS 连接凭据。新入口按项目 plugin profile 接入 bos-plugin；旧兼容入口不自动启用查询或其它插件。提交复用 demand-delivery-plugin，不依赖 IRIS 配置。

## 模式参数（用户入口）

以下是传给 Agent 的 skill 参数，不是 `demand-entry.js` 的 CLI 参数。Agent 解析模式后执行对应步骤，用户不需要编写 spec 或运行脚本。

| 模式 | 用途 | 底层动作 |
|---|---|---|
| `--help` | 显示用法，不读写业务仓库 | 无 |
| `--text` | 从已确认代码生成；明确给出提需主题/接收组时按主题生成，`--work` 从工作记录生成 | 按来源取证/整理 → 同一 prepare |
| `--work`（附加开关） | 工作记录来源，单独使用等同 `--text --work` | Agent 整理事实 → prepare，跳过 Git collect |
| `--split`（附加开关） | 显式展示拆合审查，单独使用等同 `--text --split` | 取证后审查 → 复用 prepare |
| `--excel`（附加开关） | 导出同一批条目的导入表，可与 `--split` 组合 | 复用 prepare/render 的 Excel 输出 |
| `--bind <需求号>` | 回填编号与标题；代码输出提交消息，主题/工作记录只展示映射 | bind，代码再 message |
| `--plan` | 根据已绑定草稿生成完整提交信息 | worktree：plan；history：message |
| `--commit` | 明确授权所选需求的本地提交，不包含 push | plan → demand-commit apply --confirm-commit --verify |

```text
$bos-demand-entry --help
$bos-demand-entry --text
$bos-demand-entry --text 提需求给支持组，解决演示系统登录时报授权信息不可获取的问题
$bos-demand-entry --work
$bos-demand-entry --work --split --excel
$bos-demand-entry --split
$bos-demand-entry --excel
$bos-demand-entry --split --excel
$bos-demand-entry --split --range HEAD~3..HEAD
$bos-demand-entry --text --excel --module-code DT-20
$bos-demand-entry --text --range HEAD~3..HEAD
$bos-demand-entry --text --rev abc123 --rev def456 --Excel
$bos-demand-entry --bind 7060431 --title "BOSS 最终需求标题"
$bos-demand-entry --bind 7060431 --same-title
$bos-demand-entry --plan
$bos-demand-entry --commit
```

附加参数：

- `--work`：仅 `--text` 可用，可与 `--split`、`--excel` / `--Excel` 组合；省略模式统一进入 `--text`。不与 `--rev/--range/--repo/--file`、`--bind/--plan/--commit` 混用。来源位置、日期及范围通过自然语言指定，不猜测日记目录或扫描私人资料。首版代码与工作记录分批处理，不能重复计算同一成果。回填时只用 `--bind`，由草稿识别来源。

- `--split`：仅 `--text` 可用，按下方“拆分审查”展示拆合依据，不强制多条。未指定模式且提供 `--split`、`--excel` / `--Excel` 任一开关或二者组合时，统一进入 `--text`；其它参数继续遵循本表，不因省略模式放宽校验。
- `--excel` / `--Excel`：仅 `--text` 可用，额外生成导入表；单独使用视为 `--text --excel`。`--module-code <编码>` 仅与 Excel 输出搭配，写入草稿 common 的模块编码，不猜测编码。
- `--rev <hash或ref>` 可重复，或 `--range <base>..<head>`：仅 `--text` 可用，二者互斥；缺省使用本次已确认的未提交改动。Agent 将 `--rev` 转成 collect 的 `--commit` 参数；用户层 `--commit` 始终表示正式提交，不能用来指定历史 hash。
- `--repo <GitRoot>`、`--file <精确路径>`（可重复）：仅代码来源 `--text` 可用。缺省复用本任务已确认的仓库与文件，不自动扫描整个工作区或选最近提交；来源范围不明确时补问。主题资料的位置用自然语言指定，不把附件路径当 Git 文件。
- `--item <key>`：用于 `--bind/--plan/--commit`；草稿只有一条需求或当前条目已明确时省略，否则补问要处理哪个 key，不默认批量提交。
- `--draft <draft.json>`：用于 `--bind/--plan/--commit`，跨会话时提供；同会话复用最近明确的有效草稿。找不到唯一草稿时补问，不全盘搜索。
- `--title "最终标题"` 或 `--same-title`：仅 `--bind` 可用，二者互斥；`--same-title` 表示用户确认 BOSS 沿用所选条目的原始 title。均缺省时仅在上下文已确认最终标题时复用，否则补问。

业务模式必须单选，`--work`、`--split` 和 `--excel` 是附加开关而非独立模式。未知参数、缺参数值、无效组合或显式模式与自然语言意图冲突时显示用法并停止，不执行写入。`--split` / `--excel` 不与 `--bind/--plan/--commit` 搭配；`--help` 与执行参数混用时按首段统一帮助路由结束，并说明执行参数未执行。无模式且无上述开关时继续按明确自然语言路由。`--bind` 不可与 `--commit` 合并，先保存映射并展示消息，再由单独的提交模式表达授权。

`--plan` 完成后不追问是否提交；`--commit` 已表示所选需求本地提交授权，展示计划后直接沿用原提交门禁，不重复询问。历史来源的 `--plan` 明确报告“仅生成历史提交对应消息，未创建可执行提交计划”；历史来源的 `--commit` 在 Git 写入前停止，不隐式改写历史。所有模式固定 standard，不修改工程默认类型。

## 需求名称与标版标签（各类来源共用）

生成 spec 前逐条确定产品标识及名称。产品标识取自项目明确约定或本次用户输入；迁移项目的默认值读取 `.agents/config/demand_delivery_profile.md`，明确项目约定或用户输入优先。代码/工作来源未确定产品标识时一次补问，不从技术栈猜测；主题来源未知时按下节处理。

IRIS 需求按交付目标是否改变标版产品本身判断 `[标版]`，计划开发和已完成开发适用同一规则：

| 需求目标 | 名称示例 |
|---|---|
| 修改标版代码、产品配置或 UI | `{IRIS}[标版] 医生站-处方录入-完善必填校验` |
| 会议、方案讨论 | `{IRIS} 处方流程需求讨论` |
| 演示、培训 | `{IRIS} 医生站功能演示` |
| 造数据、准备演示样例 | `{IRIS} 演示样例数据准备` |
| 临时脚本、演示环境配置调整 | `{IRIS} 演示环境准备` |

主题提需尚无代码，只要明确要求修改标版产品，也加标签；Git 中存在代码或配置改动时仍按用途判断，临时脚本和演示环境准备沿非标版工作处理。`source` 表示事实来源，`kind=standard` 表示录入流程，二者均不决定标签。混合材料沿现有拆分规则按独立目标整理，每条分别判断；标版开发中的配套会议、测试或数据准备归所属开发需求，独立工作目标才单列。

标版名称采用 `{IRIS}[标版] 业务端-功能入口-问题或目标`，标签紧接产品标识且只出现一次；其它 IRIS 需求采用 `{IRIS} 工作目标或问题`。其它产品沿项目约定，不默认替换产品标识或套用 IRIS 标签规则。名称使用已核实的业务名称，正文不重复名称或内部 title。

由 Agent 将判定后的完整名称写入现有 `name`；脚本仅校验格式，不根据来源、关键词或文件类型判断业务属性。默认 `title` 只去除产品标识，保留 `[标版]`；显式 `title` 和回填的 BOS 最终标题保持原文。文本与 Excel 共用名称，标签不自动映射 Excel 的“加入标准版”等字段。旧草稿名称保持原文，不自动补标签。

## 来源选择与主题提需

- 明确“给某组提需求”“解决某问题”并提供主题/资料，按主题来源 `source=request`，无需额外开关。`--text` 只选择输出模式，不强制 Git；“根据本次改动/提交补需求”仍走代码，`--work` 保留工作记录语义。不能因当前有代码改动而覆盖用户指定主题。
- 从用户主题提取接收组、问题/目标、发生环境、影响和预期结果，按需读取其指定文字、截图、附件及相关上下文。材料中的现象与建议分开；报错按原文引用，未经调查的原因只标为推断，不把用户反馈写成已复现。资料冲突时先核对影响正文的事实，不扫描无关仓库或私人资料。
- 接收组保存为 `recipientGroup` 并在交付说明中展示；它不等于产品标识、模块编码、BOS 产品组或具体指派人，不自动推断这些字段，也不继承当前维护仓库的产品标识。产品标识已有明确值时按上方共用名称规则处理；仅主题提需在未知时可先使用已知系统/业务入口和问题组成名称，资料足够生成正文就先交付，不为非必要字段阻塞文本。
- 缺陷沿用下方 bug 三段式，功能/改进沿用 change 三段式；不套用工作目标/内容。只补问会改变问题、范围或预期的必要未知项，不虚构账号、URL、日志、版本、复现动作或修复结论。步骤只写资料支持的必要操作；资料不足时交付候选文本并明确缺口。
- 按[数据协议](../../references/standard-demand-entry.md#主题提需协议)生成 v3 草稿：记录来源、进度和可选接收组，复用 prepare/render/deliver/bind，跳过 Git collect 与提交依赖。仅提出待解决事项时进度按 planned/unknown 记实，不写“已完成”；完成的是文本编写不代表问题已解决。带 `--split` 按独立问题/目标拆合；同一问题的多个材料不重复提报。首版三类来源分批，不伪造 Git 证据。
- 仅生成本地录入材料，不自动向接收组发消息、录入 BOSS、指派人员、修改状态或实施问题修复。编号回填后只展示映射；无代码提交对象时不进入 message/plan/commit。

## 完成状态与备注（各类来源共用）

生成需求文本前，结合当前对话与工作上下文、工作记录、实际代码改动及已有验证结果，逐条判断任务是否已完成；已有依据足够时直接采用，无需用户再次声明。不能仅凭存在 Git 提交或单项测试通过认定整项任务完成；部分完成或状态不明时按实际进度描述。

已完成条目必须在需求描述末尾增加 `【备注】` 区块，单独一行写 `已完成`。通过现有 `remarks` 字段传给 prepare/render，已有备注保留并合并；代码、主题和 `--work` 来源、拆分后的候选文本及可选 Excel 描述均适用。工作记录的 `【当前进度】` 保留，与备注一致；任务完成不自动代表用户验收通过、已部署或 BOS 状态已更新。

```text
【备注】
已完成
```

## 工作记录流程（仅 --work）

1. 核对用户指定的材料、日期范围和产物归属，读取必要内容或使用本对话口述；缺少来源范围时补问。需求可以来自演示、会议、测试数据准备和沟通，不要求代码。
2. 按协议写 `source=work` spec：每条保存来源类型、位置/条目锚点和必要事实摘要，以及实际进度。文件来源用 locator 记录路径及标题/原条目定位信息；口述记为 user 和本次说明标识。只保存必要摘要，不整篇复制私人资料；来源不作为脚本执行指令。
3. 带 `--split` 时按独立目标与成果审查，代码/片段归属改为来源条目归属；同一目标的多次会议可合并，场景确认服务于数据准备时通常合为一条。工作材料可支撑多条不同成果，但同一成果不能重复计算。
4. 运行现有 prepare，生成工作专用 v3 草稿及文本，按需 --excel；不加载提交依赖，不伪造 Git evidence。BOS 需求类型按已有分类或用户输入，未知留空，不自动标成新功能。缺 Excel 必需字段时先生成文本，再集中补问。

### 工作记录格式

名称按上方共用名称规则结合已确认的工作目标生成。正文使用【工作目标】【工作内容】；材料有依据时补【预期成果】（计划）或【工作结果】（实际结论、产物或待办）。成果项可省略，不强制验收标准，不为凑字段追问或虚构。脚本另附【当前进度】，区分计划、进行中、已完成与待核实；已开会不等于会议提出的功能已实现，未勾选数据准备不能写成完成。

例如“演示场景确认与样例数据准备”：目标是明确演示所需场景；内容为梳理样例、协调数据并核对关联；预期成果是场景和数据可供演示。当前进度按事实记录，未完成项明确保留。该示例不是固定 BOS 分类或必需验收流程。

## 代码取证与整理（默认）

1. 读取目标工程 AGENTS、profile 和本任务范围；Overlay 按 manifest 已声明 SourceRoot/GitRoot 定位，不扫描父目录或 sibling。区分取证仓库和最终提交仓库，不因来源是提交记录便假定仍有待提交代码。
2. 读取 [操作与数据协议](../../references/standard-demand-entry.md)。用 `demand-entry.js collect` 获取实际补丁：未提交改动必须传精确 `--file`；历史使用指定 `--commit`（可多次）或 `--range`。每条需求每仓库一份取证；跨仓库保持各自归属。脚本只读 Git，不执行 pull/add/commit。
3. 必须阅读取证 JSON 中 staged/unstaged/history.patch 和未跟踪内容，必要时补读关联源码与验证记录；不能只凭提交标题、文件名推断业务效果。二进制、非 UTF-8 内容和外部运行行为不能凭补丁证明，明确证据限制。确认同一文件没有混入其它需求，否则先按既有工具拆分，不自动提交整文件。
4. 按独立业务目的拆条目。新增功能、功能改进和缺陷修复均可形成需求；测试、兼容与内部配套归入服务的需求。带 `--split` 时先完成下方拆分审查；未带时保留现有业务目的拆分规则，不强制展开审查表。按下方简洁模板，用业务语言编写名称和描述；实际现象须有用户描述、复现或源码证据，源码推断注明“根据代码分析”，不写成已复现。仅影响复现或验收判断的必要未知项才集中补问。
5. 按协议的 `description` 结构写新 spec，运行 `prepare`，默认生成 `draft.json` 和逐条 `<key>.txt`；需要时加 `--excel`。文本与 Excel 描述使用同一渲染函数。交付时直接引用生成的名称和描述，分别提供可复制文本块；归属与验证信息留在草稿和交付说明中，不再手工缩写成另一版正文。

## 拆分审查

`--split` 在取证之后、生成 spec 之前执行，沿用同一流程：

1. 代码需求以独立问题或业务成果、可独立判断的验收标准、值得单独追踪为依据；工作记录按独立工作目标和已有或预期成果判断，不要求额外验收标准。公共能力和业务落地各有独立价值时可分条并标明依赖；测试、部署、兼容、加 Parameter 或提取方法等配套通常归所属需求。不按文件数、方法、阶段、代码行数或目标条数机械拆分，也不重复计算公共能力。
2. 展示简洁审查表：每条的价值、范围、代码验收点或工作成果、代码/片段或来源条目归属、依赖及拆合理由。只有一个独立目的时明确建议保留一条。通过真实问题、改动边界、影响范围和验证证据体现工作量，不虚构工时、成果或验收事实。
3. 边界明确且符合各自来源约束时，直接生成同一批条目的对应格式文本、draft 和可选 Excel，不固定增加确认环节。只有影响拆合的业务取舍无法从事实确定时才询问。
4. 业务可独立验收但共享文件不宜拆时，按[代码归属协议](../../../../docs/demand-code-ownership.md)组织一级主子需求：主需求唯一持有证据，子需求引用主需求，使用v4草稿生成全部文本及关系说明，可选Excel仍为原29列。无共同业务目标的独立需求继续执行共享文件拦截，交付候选与片段归属，等待隔离，不能重复分配整文件或改写历史。

这些是 Agent 解释的 skill 参数，不能把 `--split` 直接传给底层脚本；拆分开关不改变脚本 CLI；扁平代码保留v2，主子代码使用v4，主题/工作记录保持v3；具体字段见数据协议。审查表留在交付说明，不把技术归属与依赖表塞入 BOS 三段式正文。

选中parent子需求调用message/plan时，展示主需求归属及对应消息，返回canCommit=false；由用户或既有范围明确选择主需求后才执行正式计划。none返回不适用及原因，不加载提交依赖。全部关联子项通过前只允许已有授权的阶段恢复点；该分组不改变提交权限。

## 代码与主题简洁录入模板

- **需求名称**：按上方“需求名称与标版标签（各类来源共用）”生成；描述正文不重复名称、标题或 `content` 标签。
- **缺陷**（`description.format=bug`）：`【操作步骤】→【预期结果】→【实际结果】`。实际结果描述修复前现象；步骤包含复现所需操作，异常恢复仅在本次改动涉及时补充。
- **新功能、功能改进**（`description.format=change`）：`【需求说明】→【操作步骤】→【预期结果】`。步骤描述交付后的使用/验证方式，预期写清可观察的行为。
- 用户、安全组、科室已有且相关时写入步骤；缺失时省略，不为这些常规信息追问。只有问题依赖特定用户、权限、安全组或科室时，才作为必要条件补齐。共享模板和示例不保存业务账号或连接信息。
- 面向熟悉业务的测试组，正文采用三段式，不展开测试编号、独立测试前提或回归清单；已完成时按上方共用规则追加 `【备注】`，影响复现或验收的限制也合并到该区块。其余进度与验证详情留在交付说明。
- 操作须能执行，预期须能判断；特殊异常写明必要的触发和恢复方法。先查源码与已有资料，只补问会改变复现或验收结论的信息，不编造环境、业务事实或验证结果。

生成文件前按 [交付与私有草稿目录](../../references/demand-directories.md) 实际解析并传入本次目录；项目明确约定优先。治理启用时，文本/Excel 使用交付根，可能含补丁的 draft 使用当前 ContextRoot 的私有根，通过 `--draft-output` 分离；未启用时保留 legacy 单目录。恢复使用返回 JSON 的 `draft` 路径（旧调用为交付目录内的 draft.json），给 BOSS 的仍只有用户选用的文本或 Excel。临时 spec/取证沿工程临时规则，恢复草稿不自动进 Git、不扫描其它任务。

## 用户返回 BOSS 编号

- 使用 `bind --item <key> --demand <编号> --title <BOSS最终标题>` 保存新草稿；一条需求对应一个编号，不假定多个编号的顺序。回填最终标题是预期动作，保留原始草稿标题作来源，不要求两者字面相同。若 BOSS 内容实质改变业务范围，先复核代码和需求映射。
- 主题/工作记录回填编号后只展示条目、编号、最终标题及新草稿位置，不运行 message/plan/commit。bind 仅写草稿，不自动改来源文件；用户另行明确要求“回填来源”时，先回读并定位原条目，再追加编号，保留正文、进度及勾选状态。定位不唯一、来源变化或多对多映射先核对；口述无可写来源时不回填。当前脚本不提供来源写回能力。
- 代码闭环任务中回填编号后，直接运行 `message` 输出每仓库完整三行 standard 消息，不重复询问是否继续。只给需求号没有最终标题时，仅在用户已明确 BOSS 沿用原题时复用原题，否则补问最终标题。
- `message` 先检查证据。工作区/暂存区/HEAD 漂移时重新取证、复核内容并形成新草稿，保留已确认的 BOSS 映射；不能沿用旧代码说明。历史提交使用固定完整 hash，不因当前分支前进而失效。
- 纯历史来源到消息生成即完成该阶段；不创建空提交，不自动 amend/rebase/cherry-pick。用户若要求修改历史或移植到另一仓库，应作为明确的独立操作处理，不把原始已提交文件假装成当前变更。

## 正式提交

主题/工作记录不进入本节；误请求 plan/commit 时说明“无代码提交对象”，不改 Git。代码来源执行 prepare/message/plan 前，按[可用性依赖协议](../../../../docs/plugin-availability.md)检查 bos-plugin 的 standard-demand-entry 阶段；正式提交再检查 demand-commit 阶段。脚本按需加载提交能力，取证、回填和渲染可独立执行。

只对 worktree 来源使用 [demand-commit](../../../demand-delivery-plugin/skills/demand-commit/SKILL.md)：`demand-entry.js plan` 校验草稿后转交原 `commit-demand.js plan`，固定 `--kind standard`，复用精确文件、每仓库修改说明、BOSS 编号与最终标题。不能把 draft 当作 commit plan，也不能手工编辑生成的 plan。

生成消息或回填编号不授权 commit。用户明确要求提交时，沿用已有授权展示 plan 后执行原 `apply --confirm-commit --verify`，不重复确认；pull 门禁、漂移停止和多仓库部分成功报告均沿用原 skill。已完成验证的有效证据复用，未知验证状态如实报告。push、部署与 BOSS 写入不包含在本流程；BOSS 由用户录入。提交不改变业务验收状态。

无专用 Question 工具时用简短文本补问；无此脚本运行能力时可只读 Git 并生成带明确来源的文本/消息，不宣称已保存草稿、生成 Excel 或执行提交。
