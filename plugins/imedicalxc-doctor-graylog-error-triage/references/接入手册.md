# Graylog 报错与慢请求巡检 · 接入手册

适用对象：要在本机接入 `imedicalxc-doctor-graylog-error-triage` 的团队成员。读完本文即可从零跑到定时巡检。

`SKILL.md` 是给 AI 助手用的执行向导，人不需要先读。四份文档的分工：

| 想知道 | 看哪份 |
|---|---|
| 怎么装、怎么改配置、怎么排障 | 本文 |
| 它每天产出什么、报告怎么读 | `使用指南.md` |
| 部署是否合格、如何逐项验收 | `acceptance-checklist.md` |
| 某个已修缺陷的分析过程 | `缺陷案例-*.md` |

## 它做什么

由两个 Qoder 自动任务驱动（采集轮 cron `0,15,30,45 * * * *`，分析轮 cron `7,37 * * * *`，**不依赖 Windows 计划任务**），增量抓取 Graylog 的 **ERROR 日志 + 耗时 ≥ 15 秒的慢请求日志（两路并集）**，按堆栈或接口全限定名判定「这是谁的问题」，初判 P0/P1 严重度，产出四类文档：

| 归属 | 判定依据 | 处理方式 |
|---|---|---|
| 本组（医生站） | 堆栈里有医生站业务帧；慢请求看接口全限定名 | 出根因与修正方案 / 耗时归因与优化方案 |
| 基础设施 | public 7 仓的包前缀 | 仅落盘汇总，不推送 |
| 他组 | 应用名匹配外部产品组；慢请求优先按接口包前缀 | 生成可原样转发的文档 |
| 无关 | 他组自身故障、本组未参与 | 仅统计，不推送 |
| 待定 | 无法判定 | 进人工确认队列 |

严重度由脚本初判，分析轮可改判（须写依据）：

| 严重度 | 覆盖范围 | 处理要求 |
|---|---|---|
| **P0** | 不可预知的程序异常 | 必须给出代码修改或报错处理方案 |
| **P0** | 接口耗时 ≥ `query.slowThresholdMs`（当前 15000） | 必须分析耗时原因：数据量正常长耗时 还是 代码缺陷 |
| **P1** | 业务正常处理抛出的异常 | 确认业务语义与提示文案，不强制改代码 |

慢请求阈值**按解析出的耗时毫秒数判**，不能靠日志文案：`LogFilter` 的分档文案最高只到「超过15秒」，一次 2101 秒的调用也写着「超过15秒」。当前阈值 15s 虽与最高档同档，但文案是「超过」语义、阈值是 `>=`，且档位阶梯不透明，所以 `tier` 只作展示，判定始终走毫秒数。

产物统一落在 `docs/agent-reports/graylog-triage/<env>/<yyyy-MM-dd>/`。

## 0.写在前头-关于 `<env>`

命令里的 `<env>` 是**环境名**。它不是随便起的别名，而是 `config/graylog-triage.json` 里 `environments` 对象的 **key**，必须一字不差地照抄：

```text
environments
├── "87"             label: 87 环境
└── "wengyuan-prod"  label: 翁源生产环境
```

常见的几种写法与结果：

| 你写的 | 结果 |
|---|---|
| `-Env wengyuan-prod` | ✅ 使用 `environments["wengyuan-prod"]` 的连接与采集策略 |
| `-Env wengyuan` | ❌ `exit 2`，并提示可选值 `87, wengyuan-prod` |
| `-Env WENGYUAN-PROD` | ❌ 区分大小写，同样 `exit 2` |

还有一套参数写法容易和上面混：**node 脚本用 `--env`，PowerShell 脚本用 `-Env`**。混用不会报错，而是**静默退回 `defaultEnv`**——输出看着正常，跑的却是另一个环境。

```powershell
# node 脚本：双连字符
node .agents\plugins\imedicalxc-doctor-graylog-error-triage\scripts\collect-errors.js --env wengyuan-prod --check

# PowerShell 脚本：单连字符
powershell -NoProfile -ExecutionPolicy Bypass -File .agents\plugins\imedicalxc-doctor-graylog-error-triage\scripts\run-triage.ps1 -Env wengyuan-prod -SkipNotify
```

一个环境名同时决定下面五件事，且全部按环境隔离。这也是为什么换环境不用清状态、两个环境可以并存：

| 决定什么 | 填 `wengyuan-prod` 时的实际值 |
|---|---|
| 连哪台 Graylog | `mcp.json` 里 `mcpServers["graylog-wengyuan-prod"]` 的 `env` |
| 水位线 + 去重表 | `config/graylog-triage-state-wengyuan-prod.json` |
| 运行日志 | `config/logs/triage-<yyyyMMdd>-wengyuan-prod.log` |
| 报告目录 | `docs/agent-reports/graylog-triage/wengyuan-prod/` |
| Qoder 自动任务名 | `医生站 Graylog 报错采集轮（wengyuan-prod）` + `…分析轮（wengyuan-prod）`（回退到 OS 调度时为 `iMedicalxc-GraylogTriage-wengyuan-prod`） |

查本机有哪些可选值（key + 中文名 + 是否启用）：

```powershell
node -e "const c=require('./.agents/plugins/imedicalxc-doctor-graylog-error-triage/config/graylog-triage.json');Object.entries(c.environments).forEach(([k,v])=>console.log(k,'|',v.label,'|',v.enabled?'enabled':'disabled'))"
```

输出形如：

```text
87 | 87 环境 | enabled
wengyuan-prod | 翁源生产环境 | enabled
```

> 新增环境见第 5 节。停用旧环境、启用新环境的完整步骤见 `使用指南.md` 第 5 章「换环境」。

## 2. 快速接入（5 步）

> 所有命令都是单行。请逐条粘贴执行，不要一次粘贴多行——PowerShell 5.1 控制台多行粘贴可能倒序执行。

### 步骤 1：自检插件文件

```powershell
node .agents\plugins\imedicalxc-doctor-graylog-error-triage\scripts\verify-install.js
```

输出里「插件文件完整性」若显示缺失，先补齐再继续。

### 步骤 2：注册 Graylog 连接（唯一必填项）

打开 `%USERPROFILE%\.qoder-cn\shared_client\mcp.json`，加入：

```json
{
  "mcpServers": {
    "graylog-<env>": {
      "command": "node",
      "args": ["<你的仓库绝对路径>/mcp-graylog/index.js"],
      "env": {
        "GRAYLOG_URL": "http://<Graylog地址>:端口号",
        "GRAYLOG_TOKEN": "<只读token>"
      }
    }
  }
}
```

三条硬性要求：

1. **`args` 必须是本机绝对路径**。这是同事接入最常见的失败原因——直接复制别人的配置，路径指向别人的机器。正斜杠或双反斜杠都可以。
2. **`env` 里的变量名固定**为 `GRAYLOG_URL` / `GRAYLOG_TOKEN` / `GRAYLOG_COOKIE`，不要写成 `GRAYLOG_87_URL` 这种带环境 ID 的形式。带环境 ID 的名字属于另一层：只在进程环境变量或 `.qoder/settings.local.json` 里用，对应配置里的 `urlEnv` / `tokenEnv` / `cookieEnv`（如 `GRAYLOG_WENGYUAN_PROD_URL`）。两层混用会解析不到。
3. **此文件不入库**。它位于用户目录，每人各配一份，互不冲突。

> `graylog-<env>` 这个 key 必须与配置里的 `environments.<env>.mcpServer` 完全一致，否则报 `status: missing-config`。

### 步骤 3：连接预检

```powershell
node .agents\plugins\imedicalxc-doctor-graylog-error-triage\scripts\collect-errors.js --env <env> --check
```

期望输出 `"status": "ready"`。不通过时对照第 6 节排障表。

### 步骤 4：手动跑一轮

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .agents\plugins\imedicalxc-doctor-graylog-error-triage\scripts\run-triage.ps1 -Env <env> -SkipNotify
```

`-SkipNotify` 跳过推送，避免没配推送时被卡住。

> [!TIP]
>
> ##example#
> powershell -NoProfile -ExecutionPolicy Bypass -File .agents\plugins\imedicalxc-doctor-graylog-error-triage\scripts\run-triage.ps1 -Env wengyuan-prod -SkipNotify

成功判据四条，缺一条都不算通：

- 退出码为 `0`
- `docs/agent-reports/graylog-triage/<env>/<今天>/` 下出现 `raw-errors-*.json`、`classified-*.json`、`report-summary-*.md`、`report-self-*.md`
- `config/graylog-triage-state-<env>.json` 的 cursor 已推进（水位线按环境分文件，各环境互不覆盖）
- 日志里**两路计数齐备**：`报错命中 N 条` 与 `慢请求（>=15s）命中 N 条，取回 N 条，达标 N 条`。达标 0 条可以是正常结果（窗口内确实没有超阈值接口），但整路计数缺失说明 `query.slowSelector` 被清空，须先排查

### 步骤 5：创建 Qoder 自动任务（采集轮 + 分析轮）

调度主体是 Qoder 自动化（`qoder_cron`），**不需要注册任何 Windows 计划任务**。在「自动化」面板新建，或会话内用 `qoder_cron` 的 `add`：

| 项 | 采集轮 | 分析轮 |
|---|---|---|
| 名称 | `医生站 Graylog 报错采集轮（<env>）` | `医生站 Graylog 报错分析轮（<env>）` |
| cron（Asia/Shanghai） | `0,15,30,45 * * * *` | `7,37 * * * *` |
| 权限 | **Full Access**（`executionAuthorization: true`） | Auto Approval（`false`） |
| outputMode | `merged` | `merged` |
| cwd | 仓库根目录 | 仓库根目录 |
| prompt | 只跑 `run-triage.ps1 -Env <env>` 一条命令 + 退出码回报协议 + 禁止清单 | 读主 skill，按 `pending-queue.json` 全量候选 **P0 优先**做根因分析 / 慢请求耗时归因（每轮上限 4 条）；禁采集、禁外发、禁改任何调度 |

触发点故意错开（采集 :00/:15/:30/:45，分析 :07/:37），分析轮读到的一定是已落盘的完整一轮。

**采集轮为什么必须 Full Access**：Auto Approval 的权限分类器把 `powershell -NoProfile -ExecutionPolicy Bypass` 判为任意代码执行直接拦下。实测后果是任务状态显示 `succeeded`、耗时十几秒，但日志 mtime 不动、cursor 不推进、一个产物都没有——**状态成功不等于流水线跑了**。分析轮保持 Auto Approval 即可（它只读报告、跑 node 脚本、写队列），无人值守不放开远端写入。

创建后用 `qoder_cron` 的 `run` 立即触发一次验证，判据只看客观证据：

- `config/logs/triage-<yyyyMMdd>-<env>.log` 的 mtime 推进，且末尾有本轮 `[SUMMARY]`
- 当日报告目录出现本轮 HHmm 的 `raw-errors-*` / `classified-*` / `report-summary-*` / `report-self-*`
- `config/graylog-triage-state-<env>.json` 的 cursor 已推进

三项齐了才算通。`lastRunStatus: succeeded` 只代表会话结束，不作为判据。

#### 可选回退：OS 计划任务

只有需要「Qoder 客户端退出期间也采集」时才用。**启用前必须先 `disable` Qoder 采集轮**，避免双调度。

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .agents\plugins\imedicalxc-doctor-graylog-error-triage\scripts\install-schedule.ps1 -Env <env> -DryRun
```

确认以下三项后，去掉 `-DryRun` 正式注册：

- `Repeat   : 无限期`
- `Principal: <你的账号> / Interactive / Limited`
- 触发间隔与 `config.schedule.intervalMinutes` 一致（当前 15 分钟；OS 路径只认这个值，改 cron 不影响它）

注册后立即触发一次验证：

```powershell
Start-ScheduledTask -TaskName "iMedicalxc-GraylogTriage-<env>"
```

```powershell
Get-ScheduledTaskInfo -TaskName "iMedicalxc-GraylogTriage-<env>" | Select-Object LastRunTime, LastTaskResult, NextRunTime
```

`LastTaskResult` 判读：

| 值 | 含义 | 下一步 |
|---|---|---|
| `0` | 正常 | — |
| `267009` | 正在运行 | 等它结束 |
| `1` | 脚本失败 | 查 `config\logs\triage-<日期>-<env>.log` |
| `2` | 连接不可用 | 回到步骤 3 |
| `3` | 另一轮正在执行 | 正常跳过，不用处理 |

### 可选：推送

不配置时每轮只在日志里留一条 `[WARN] 推送未配置`，不阻断任何产出。要配置见第 5 节。

### 可选：前端索引

**先明确一件事：构建索引不会改变当前精度。**

`penetrate-frontend.js` 的 `effectiveMode` 目前硬编码为 `heuristic`，codegraph 分支尚未实现。所以无论建不建索引，报告给出的都只到候选页面级，不会精确到按钮和 JS 行号。

建索引的真实价值，是让报告里的「精度说明」从含糊的「索引未构建」变成具体事实判断（本轮无本组簇 / 全是服务间调用 / 索引在但分支未实现）。

不构建也能正常巡检，不影响任何报告产出。要构建：

```powershell
node .agents\plugins\imedicalxc-doctor-graylog-error-triage\scripts\build-front-chains.js --build --python "<Python 解释器绝对路径>"
```

`--python` 必须给绝对路径。Windows 上 `python` 和 `python3` 大概率指向 Store 占位符，脚本的自动探测（`python` → `py -3` → `python3`）三条全失败。取真实路径：

```powershell
py -3 -c "import sys; print(sys.executable)"
```

输出形如 `C:\Users\<你>\AppData\Local\Programs\Python\Python312\python.exe`，把它填进 `--python`。

正式跑之前先加 `--dry-run` 预演，四个步骤都列出来再动手：

```powershell
node .agents\plugins\imedicalxc-doctor-graylog-error-triage\scripts\build-front-chains.js --build --dry-run --python "<路径>"
```

实测耗时 **50 秒**、产物约 **342MB**，且已被 `docs/agents/.gitignore` 排除（`*.jsonl`、`front_chain_db.json`、`controller_endpoints.json` 均已覆盖）：

| 文件 | 大小 | 内容 |
|---|---|---|
| `controller_endpoints.json` | 7.6MB | 1686 个 Controller / 11563 条 URL |
| `front_chain_db.json` | 72MB | 6015 页面 / 38350 条链路 |
| `front_js_index.jsonl` | 176MB | 9071 个 JS 文件的词法索引 |
| `front_pages.jsonl` / `front_elements.jsonl` / `front_chains.jsonl` | 87MB | 178621 个操作元素 |

重建时机：前端 `static/` 大面积改动，或后端新增 Controller 之后。

## 3. 日常使用

### 3.1 每轮先看哪份

| 文件 | 什么时候看 |
|---|---|
| `report-summary-<HHmm>.md` | 每轮先看这个，一分钟扫完**严重度分布（P0 优先）**与归属分布 |
| `report-self-<HHmm>.md` | 有本组 P0 时细看：开头是 P0 优先索引，正文含堆栈与修正方案，慢请求簇含耗时样例与耗时归因 |
| `notify-<组>-<HHmm>.md` | **手工转发**给对应产品组 |
| `report-infra-<HHmm>.md` | 排查底层问题时看 |

### 3.2 哪些文件会被自动删除

`notify-*.md` 和 `report-infra-*.md` 是**状态快照**，只保留最新轮次。某个组本轮不再报错，它的旧通知会被自动删除——这是刻意设计，避免有人照着过期通知误判问题仍在。

`report-self-*.md` 和 `report-summary-*.md` 是历史轨迹，永不自动清理。

### 3.3 单轮日志

```
.agents\plugins\imedicalxc-doctor-graylog-error-triage\config\logs\triage-<yyyyMMdd>-<env>.log
```

日志按环境分文件，多环境同时跑时各写各的；需要二次确认时，看日志里的 `环境=<env>` 行。

**有自动清理**：`run-triage.ps1` 每轮末尾按 `output.runLogKeepDays`（当前 14 天）删除 `config/logs/` 下 `LastWriteTime` 超期的 `triage-*.log`，配 0 或负数则不清理。注意 `output.runLogDir` 这个配置键脚本并不读取，日志目录硬编码为 `config/logs/`。

### 3.4 摘要里的「精度说明」

`report-summary-<HHmm>.md` 中那行前端信息会随情况变化。四种形态含义完全不同，不要混看：

| 精度说明文字 | 对应 `degradeReason` | 含义 | 需要处理吗 |
|---|---|---|---|
| 未构建 codegraph 前端索引… | `index-missing` | 索引文件不存在 | 想改善就按第 2 节构建 |
| 本轮无本组或待定簇，未产生界面定位需求 | `no-target-cluster` | 本组 0 簇、待定 0 簇 | 不用，正常轮次 |
| 本组簇均无浏览器发起的请求… | `no-frontend-entry` | 全是 Feign 服务间调用或后台任务 | 不用，这类报错本来没有界面入口 |
| codegraph 索引已构建，但穿透脚本尚未启用按钮级分支 | `codegraph-index-present-but-codegraph-mode-not-enabled` | 索引在、有浏览器请求，但分支没写 | 技术债，等分支实现 |

前三种都是客观事实，只有第四种是真待办。早期四种情况混报同一条消息，是报告最容易被人误读的地方。

**慢请求簇会推高第三种形态**：`LogFilter` 的慢请求日志只有接口名与耗时，不含请求 URL，穿透层一律判为 `no-http-request` 并跳过。所以本组慢请求越多，「本组簇均无浏览器发起的请求」越容易出现——这是正确结果，**构建前端索引也不会改善**。要还原触发界面只能按簇里的 traceId 回查全链路。

### 3.5 采集口径与严重度配置

都在 `config/graylog-triage.json`，改完不需要重新接入：

| 键 | 当前值 | 作用 |
|---|---|---|
| `query.errorSelector` | `level:3` | 第一路：ERROR。命中 0 条时回退 `query.fallbackSelector`（`level_name:ERROR`） |
| `query.slowSelector` | `full_message:"接口响应超过"` | 第二路：慢请求候选。**置空即关闭这一路**，日志会打 `慢请求采集未启用` |
| `query.slowThresholdMs` | `15000` | 达标阈值，按解析出的耗时毫秒数判。单轮慢请求上限 2000 条。键缺失或非法时脚本兜底也是 15000 |
| `severity.businessLoggers` | `["com.mediway.his.server.advise.HisBusinessInterceptor"]` | 业务异常信号之一，**全等匹配** logger 名 |
| `severity.businessMessagePrefixes` | `["业务异常("]` | 信号之二，只比消息**首行**前缀 |
| `severity.businessExceptionClasses` | `["HisBusinessException", "BaseBusinessException", "BusinessException"]` | 信号之三，只比异常类的**简单名**（去掉包前缀） |

三个信号是**「或」关系**，命中任意一个即判该条为业务异常。簇级规则：整簇全是业务异常 → P1；只要有一条不是 → P0（部分业务异常时另记 `severityMixed`，报告按最高级处理）。慢请求不参与这套判定，一律 P0。

**改 `slowThresholdMs` 必须重新采集才会改变达标集合**：阈值筛选在采集阶段（`fetchSlow` 按毫秒数过滤后才落盘），分类阶段只用阈值生成「严重度依据」那行文案。所以对已有 raw 重跑分类，既补不回被丢弃的低耗时日志，也剔不掉已落盘的高耗时日志——只会改文案。

本次由 `60000` 下调到 `15000` 同理：历史 raw 里只有 ≥60s 的慢请求，**15–60s 那一段从未落盘，改配置补不回来**。要覆盖历史只能人工把 `state.envs.<env>.cursor` 回拨到缺口起点再触发一轮（受 Graylog 保留期限制，回拨操作必须记录）。好消息是慢请求 `errorHash = sha1('slow|' + 接口全限定名)` **不含耗时**，所以降阈值不会分裂已有簇，也不会让已回填的 `analysis` 结论失联；新纳入的 15–60s 调用会累加进同接口旧簇的 `count` 与平均耗时。

改归属规则或严重度信号后，才是重跑分类就能生效（不用重新连 Graylog）：

```powershell
node .agents\plugins\imedicalxc-doctor-graylog-error-triage\scripts\classify-owner.js --env <env> --file <raw-errors-*.json 路径>
```

> 初判偏保守是刻意的：配置缺失、数据校验类的 ERROR 也会先落 P0，由分析轮按业务语义改判为 P1。宁可多报一簇让人降级，也不要把真缺陷静默成 P1。

## 4. 修改 Graylog 连接

### 4.1 解析优先级

```
1. IDE mcp.json 的 mcpServers["graylog-<env>"].env
2. 环境变量 GRAYLOG_<env>_URL / _TOKEN / _COOKIE
   （也可写在 .qoder/settings.local.json 的 graylogTriage.env）
3. 两者都有且不一致 → ambiguous，直接报错，不猜
```

### 4.2 场景 A：改地址或 token（最常见）

只改 `%USERPROFILE%\.qoder-cn\shared_client\mcp.json` 里 `graylog-<env>` 的 `GRAYLOG_URL` 或 `GRAYLOG_TOKEN`，然后重跑步骤 3 的预检。

### 4.3 场景 B：改用 Cookie 鉴权

把 `GRAYLOG_TOKEN` 换成 `GRAYLOG_COOKIE`（浏览器 Cookie 串，需含 `authentication=` 片段）。代码只要求 token 或 cookie 二者之一。报告渲染时会拦截含 `authentication=` 的输出，不会泄露。

### 4.4 场景 C：换 mcp.json 位置

默认 `<用户目录>/.qoder-cn/shared_client/mcp.json`。两种改法：

- 设环境变量 `QODER_MCP_CONFIG` 指向新路径
- 改 `config/graylog-triage.json` 的 `mcpConfig.base` 为 `workspace`

### 4.5 场景 D：改默认环境

改 `config/graylog-triage.json` 顶部的 `"defaultEnv": "<env>"`（当前为 `wengyuan-prod`）。它只影响不传 `--env` 时的取值；自动任务的 prompt 里是显式传 `-Env` 的，不受影响。

## 5. 新增一个环境

以新增 `88` 为例，四处都要处理，漏一处就会在某个环节失效。

### 5.1 第一处：mcp.json 加条目

```json
"graylog-88": {
  "command": "node",
  "args": ["<你的仓库绝对路径>/mcp-graylog/index.js"],
  "env": {
    "GRAYLOG_URL": "http://<88环境地址>:9000",
    "GRAYLOG_TOKEN": "<88的token>"
  }
}
```

### 5.2 第二处：主配置加环境块

编辑 `config/graylog-triage.json`，在 `environments` 里追加：

```json
"88": {
  "enabled": true,
  "label": "88 环境",
  "mcpServer": "graylog-88",
  "urlEnv": "GRAYLOG_88_URL",
  "tokenEnv": "GRAYLOG_88_TOKEN",
  "cookieEnv": "GRAYLOG_88_COOKIE",
  "transport": "http",
  "streamIds": [],
  "retentionDays": 7,
  "overlapSeconds": 120,
  "intervalMinutes": 15,
  "pageSize": 1000,
  "maxMessagesPerRun": 12000,
  "sliceBudget": 8000,
  "maxSlicesPerRun": 4
}
```

> `intervalMinutes` **不是触发周期**：它只决定首轮回溯窗口（`interval × 2`）。真实节奏由采集轮的 cron 决定；只有回退到 OS 计划任务时才由 `config.schedule.intervalMinutes` 决定。

### 5.3 第三处：校准归属规则（最容易漏）

```powershell
node .agents\plugins\imedicalxc-doctor-graylog-error-triage\scripts\collect-errors.js --env 88 --check
```

```powershell
node .agents\plugins\imedicalxc-doctor-graylog-error-triage\scripts\classify-owner.js --env 88 --calibrate
```

`--calibrate` 会输出该环境实际出现的应用名与包前缀分布。**不同环境的服务拆分可能不同**，要确认 `ownerGroups` 的 `appPrefixes` 已覆盖全；漏了会产生大量「待定」，处理方式见 6.2。

### 5.4 第四处：创建该环境的两个 Qoder 自动任务

按步骤 5 的参数表，用 `qoder_cron` 的 `add` 建 `医生站 Graylog 报错采集轮（88）`（cron `0,15,30,45 * * * *`，Full Access）与 `医生站 Graylog 报错分析轮（88）`（cron `7,37 * * * *`，Auto Approval），prompt 里的环境名全部换成 `88`。

可与已有环境的自动任务并存：锁、水位线、日志、报告目录都按环境隔离，不会互相阻塞。建完用 `run` 触发一次，按步骤 5 的三项客观证据验收。

> 换环境（停一个、起一个）的完整步骤见 `使用指南.md` 第 5 章「换环境」。

## 6. 排障速查

### 6.1 连接类

| 现象 | 原因 | 处理 |
|---|---|---|
| `status: missing-config` | mcp.json 里没有 `graylog-<env>` 条目 | 检查 serverKey 拼写；确认 `QODER_MCP_CONFIG` 没指错文件 |
| `status: missing-credentials` | 有条目但缺 URL 或 token | 补 `GRAYLOG_URL` + `GRAYLOG_TOKEN` |
| `status: ambiguous` | mcp.json 和环境变量同时存在且不一致 | 清掉其中一方 |
| `IDE mcp.json 解析失败` | JSON 语法错误 | `node -e "JSON.parse(require('fs').readFileSync(process.env.USERPROFILE+'/.qoder-cn/shared_client/mcp.json','utf8'))"` |
| 报告全是 0 条 | 窗口内确实无 ERROR，或 selector 不匹配 | 先 `--check`，再换 `fallbackSelector` 试。注意分两路看：报错 0 条不代表慢请求也 0 条 |
| 日志只有报错计数、没有慢请求计数 | `query.slowSelector` 被清空，脚本会打 `慢请求采集未启用` | 补回 `full_message:"接口响应超过"`。这是配置问题，不是取数失败 |
| 慢请求命中很多但达标 0 条 | 阈值按毫秒数判，窗口内的慢请求都没到 15s | 正常。要确认解析没失败，看 `classified-*.json` 里有没有 `kind: slow` 的条目 |

### 6.2 分类类

**待定簇突然变多** —— 有新应用没配进 `ownerGroups`：

```powershell
node .agents\plugins\imedicalxc-doctor-graylog-error-triage\scripts\classify-owner.js --env <env> --calibrate
```

从输出里找出未归类的 app name，补进 `ownerGroups.external.appGroups` 对应的产品组。

真实案例：`mrfs-mediway-server`（病案归档）曾漏配，导致 3 个簇进待定；在 `"病案": ["mrdia", "mrqc", "mrfs"]` 里补上 `"mrfs"` 后待定归零。

**本组簇数突然从 1-2 涨到 10+** —— 某个功能在批量报错，直接看 `report-self-<HHmm>.md`。

**慢请求被误判成本组** —— 这是慢请求特有的坑，真实案例：

`com.mediway.his.ph.in.bs.controller.PhInRecController.handleAudit` 耗时 90.7 秒，打印进程是 `his-mediway-server`。因为慢请求没有堆栈帧，五步短路只能靠 app_name，结果落进「本组（仅应用名推断）」——但这是**药房药库**的接口。

判定证据不能靠猜：在 comoe / ipcare / opcare 三个子仓库里 Grep 到对 `com.mediway.his.ph.in` / `ph.ip` / `ph.op` / `ph.herb` 的 Feign import（说明本组是调用方而非实现方），再对照应用映射登记表确认归属，然后把四个前缀补进 `ownerGroups.external.packagePrefixes["药房药库"]`。补完重跑分类，该簇变成 `external / in / 药房药库`，判定规则为 `slow-interface-fqcn`。

> 术语别混：`slow-interface-fqcn` 是**判定规则名**；`evidenceLevel = interface-fqcn` 是**证据等级**，只在接口归属为本组时才写（他组簇不标这个字段，它衡量的是「本组代码证据有多强」）。

> 注意 `external.packagePrefixes` 的 ownerModule 取包前缀最后一段，所以 `ph.in` / `ph.ip` / `ph.op` / `ph.herb` 会分别落到 `in` / `ip` / `op` / `herb` 四个模块名下的同一个产品组。**不得因为「看起来像医生站调的」就把前缀塞进 self。**

### 6.3 执行类

| 退出码 | 含义 | 处理 |
|---|---|---|
| `0` | 正常（含主动跳过） | — |
| `1` | 阶段失败 | 查日志里 `[FAIL]` 或 `[TAIL]` 行 |
| `2` | 连接/配置不可用 | 回到第 2 节步骤 3 |
| `3` | 另一轮正在执行 | 正常跳过；持续出现则删 `config/.run-<env>.lock` |

### 6.4 手工重跑的参数对照

参数名写错**不会报错**，只会静默走默认值——读了错的文件却照常出结果，这是最危险的一类坑。

| 脚本 | 参数 | 说明 |
|---|---|---|
| `collect-errors.js` | `--env` / `--check` / `--limit` / `--dry-run` / `--mcp-config` | `--check` 只预检不取数；`--dry-run` 取数但**不落盘、不推进水位线**；**没有 `--from`**，补采只能人工回拨 state cursor |
| `classify-owner.js` | `--file` | 读 raw 用 `--file`，**不是** `--raw` |
| `classify-owner.js` | `--calibrate` | 输出归属校准证据 |
| `penetrate-frontend.js` | `--classified` | 读分类结果 |
| `render-report.js` | `--classified` | 必须指向刚生成的那个文件 |
| `run-triage.ps1` | `-Env` / `-SkipNotify` / `-SkipCollect` / `-Limit` / `-NoLock` | 是 `-SkipNotify`，不是 `-SkipPush`；**没有 `-DryRun`**（那是 `install-schedule.ps1` 的参数） |
| `install-schedule.ps1` | `-Env` / `-DryRun` / `-Uninstall` / `-Force` / `-UseS4U` | **仅 OS 回退时用**；**没有** `-Query` 参数；`-Force` 不能覆盖同名任务，需先 `-Uninstall` |

真实案例：曾出现 `classify` 写出 `classified-1930.json`（按当前时间命名），而 `render` 的 `--classified` 指向 `classified-1913.json`，报告内容与分类结果完全对不上，排查了很久。

## 7. 运维要点

### 7.1 磁盘

| 内容 | 量级 |
|---|---|
| 每轮 `raw-errors-*.json` | 3-12MB（视日志量） |
| 每日累计 | 约 300-500MB |
| 保留 3 天后稳定值 | 约 1.5GB 以内 |

保留天数由 `config/graylog-triage.json` 的 `output.rawKeepDays`（默认 3）控制。查看当前占用（含所有环境）：

```powershell
"{0:N0} MB" -f ((Get-ChildItem "docs\agent-reports\graylog-triage" -Recurse -File | Measure-Object Length -Sum).Sum / 1MB)
```

### 7.2 自动任务生命周期

主路径是 Qoder「自动化」面板：启停、改 cron、看历轮输出。会话内等价动作是 `qoder_cron`：

| 想做的事 | 动作 |
|---|---|
| 看两个任务的状态与下次触发 | `list` |
| 立刻跑一轮验证 | `run`（验收只看客观证据，见步骤 5） |
| 临时停 / 恢复 | `disable` / `enable`（采集轮与分析轮各自独立） |
| 改节奏 | `update` 改 cron 表达式，**不是改 `config.schedule.*`** |
| 彻底删除 | `remove` |

两个任务都**依赖 Qoder 客户端在线**，客户端退出期间不触发；重启后水位线会补齐这段窗口，不需要手工回放。要完全静默就两个都 `disable`。

自动任务不得自行创建、修改、暂停任何调度任务（含自身），调度变更只能由人工发起。

#### 可选回退：OS 计划任务生命周期

```powershell
Get-ScheduledTaskInfo -TaskName "iMedicalxc-GraylogTriage-<env>"
```

```powershell
Start-ScheduledTask -TaskName "iMedicalxc-GraylogTriage-<env>"
```

```powershell
Disable-ScheduledTask -TaskName "iMedicalxc-GraylogTriage-<env>"
```

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .agents\plugins\imedicalxc-doctor-graylog-error-triage\scripts\install-schedule.ps1 -Env <env> -Uninstall
```

任务以 `Interactive` 身份运行，**只在用户登录期间触发，不保存密码**。笔记本合盖休眠时不跑，唤醒后由 `StartWhenAvailable` 补跑一次。

需要未登录也运行，加 `-UseS4U`；代价是没有用户域凭据，访问网络共享等会受限。

`-Force` **不能**覆盖同名任务（`Register-ScheduledTask` 仍抛 `0x800700b7`），覆盖走 `-Uninstall` 再注册。

### 7.3 并发与锁

同一环境同时只跑一轮，靠 `config/.run-<env>.lock` 隔离，锁内容为 `PID|时间戳`。持锁进程已死会立即接管，锁龄超 60 分钟视为残留。多环境各自独立，互不阻塞。

## 8. 已知限制

| 项 | 现状 | 影响 |
|---|---|---|
| 调度在线要求 | 采集轮与分析轮都是 Qoder 自动任务，**客户端退出期间不触发** | 关机/退出客户端的时段没有新报告；重启后水位线补齐窗口，不漏采。需要离线也采集只能回退 OS 计划任务（并先 disable 采集轮） |
| 推送 | 未接通。目标 OneBot 服务返回 403（根路径也 403、响应体空、无 Server 头），判定为网关层拦截 | 每轮一条 `[WARN]`，需手工转发 `notify-*.md` |
| 前端定位 | `effectiveMode` 硬编码为 `heuristic`，codegraph 分支尚未实现（详见 3.4） | **即使构建了索引**也只能给候选页面，无法定位到按钮和 JS 行号 |
| 单簇海量噪音 | 主数据 `mdm-mediway-server` 常出现单簇 2000-3000 条（PG 连接拒绝） | 占采集量与磁盘，但不推送，不影响通知内容 |
| 无关组不流转（部分例外） | 他组自身故障判为「无关」后默认只统计，但 `notify.notifyUnrelated` 里登记的组例外（当前为 `["检查"]`，其无关簇内容并入对应 notify 文档） | 未登记的组（如病案组那个 Kingbase `RETURNING` 语法 bug）不会自动通知，需在 summary 里人工扫一眼 |
| 无本组簇的轮次 | 大部分轮次本组 0 簇（服务器内部流转、定时任务、DB 连接失败占多数） | 前端穿透对这类报错天然无解，不要误以为插件的定位能力失效了 |
| **慢请求端到端未实测** | 截至本次改动，没有任何一轮真实采集窗口里出现过慢请求命中。查询/解析/归属已用 24h 只读探针在真实数据上验证（**当时阈值 60s**：244 命中 / 216 达标 / 3 接口），采集→分类→渲染的衔接只用合成数据验证。阈值现已下调为 15s，达标集合只会扩大（该窗口上限 244 条），但扩大后的真实数据同样没跑过整轮 | 下一个含慢请求的采集轮才是真实验收点。届时重点看：两路计数、`kind: slow` 条目、慢请求三段报告、P0 索引里的慢请求行 |
| 慢请求无堆栈无 URL | `LogFilter` 只打接口名与耗时 | 归属靠接口包前缀，耗时归因靠 traceId 追全链路；前端定位天然为空，建索引也不改善 |

## 9. 最短路径

配好 `mcp.json` 的 `graylog-<env>` 之后，两步命令 + 一次自动任务创建即可跑完接入：

```powershell
node .agents\plugins\imedicalxc-doctor-graylog-error-triage\scripts\collect-errors.js --env <env> --check
```

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .agents\plugins\imedicalxc-doctor-graylog-error-triage\scripts\run-triage.ps1 -Env <env> -SkipNotify
```

第三步不是命令：按步骤 5 用 `qoder_cron` 的 `add` 建采集轮（Full Access）与分析轮（Auto Approval），再 `run` 触发一次。

跑完检查 `docs\agent-reports\graylog-triage\<env>\<今天>\` 是否已有报告、日志 mtime 与 state cursor 是否推进，三项齐了说明整条链路通了。
