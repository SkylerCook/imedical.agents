## 1. 缺陷定位

| 行号 | 现有代码 | 问题 |
|---|---|---|
| 1176-1179 | `catch (Exception e) { e.printStackTrace(); log.error("获取敏感字段失败{}:{}", "telHome", rtnList); }` | ① 捕获后未 `return`，继续执行 1180 行；② 日志第二个占位符打的是局部变量 `rtnList`（此时仍为空 List），不是异常 `e`；③ `printStackTrace()` 写标准错误，正式环境不进日志文件，Graylog 采集不到 |

## 2. 触发条件

三条同时成立：

1. 配置开关 `PaadmIpConfigConstants.IS_SENSITIVE_MASK`（1146 行）为 true
2. 列表中存在 `telH` 非空的患者（否则 1169-1171 行提前 return）
3. 脱敏服务 `security.getSensitiveFieldsFormatValuesByCode` 抛异常，或返回体 `data` 为 null

## 3. 影响面

- **可用性**：脱敏服务短暂抖动 → 整个住院患者列表接口 500，而不是降级展示
- **可观测性**：`log.error` 打的是空 List，堆栈只在 stdout，线上无法定位根因
- **噪音**：一次抖动同时产生「获取敏感字段失败[]:[]」和 `IndexOutOfBoundsException` 两条 ERROR
- **安全**：异常分支下 `telH` 保持原值（明文电话）原样返回前端，与脱敏目的相反

## 4. 修复建议

```java
List<SensitiveFieldFormatGroupDTO> rtnList = new ArrayList<>();
try {
    BaseResponse<List<SensitiveFieldFormatGroupDTO>> response = security.getSensitiveFieldsFormatValuesByCode(sensitiveList);
    rtnList = response == null ? null : response.getData();
} catch (Exception e) {
    log.error("获取敏感字段失败 code=telHome, patientCount={}", telHomeList.size(), e);
}
if (CollUtil.isEmpty(rtnList) || CollUtil.isEmpty(rtnList.get(0).getItems())) {
    // 脱敏不可用时 fail-safe：清空号码，避免明文外泄
    paPatStandardList.forEach(vo -> vo.setTelH(""));
    return;
}
SensitiveFieldFormatGroupDTO sensitiveFieldList = rtnList.get(0);
sensitiveFieldList.getItems().forEach(i -> {
    String patientId = i.getId();
    if (patMap.containsKey(patientId)) {
        patMap.get(patientId).setTelH(i.getValue());
    }
});
```

改动要点：

1. `response` 判空后再取 `getData()`，避免 NPE
2. `catch` 内只打日志不再吞掉后续流程，异常对象作为最后一个参数交给 SLF4J 输出堆栈
3. `rtnList` 与 `items` 双重判空，彻底消除 1180/1181 行的越界与 NPE
4. 失败分支改为 **fail-safe**（清空号码）而非 fail-open（保留明文）

无新增 import：`CollUtil`（1147 行已在用）、`FeignQueryPaPatMastStandardVO.setTelH`（1185 行已在用）均可用。

## 6. 待业务确认

**失败时清空号码 vs 保留明文**。当前代码在异常下保留明文，等于脱敏失效仍然外泄。本文建议清空（fail-safe），但这会让医生在脱敏服务故障时看不到患者电话，需业务确认是否接受，或折中为「保留但打码为 `***`」。

## 7. 本案例可复用的排查方法

### 7.1 缺陷模式

`catch` 内只打日志、不打 `return`、随后直接对可能为空的容器取值。

这类模式在 Graylog 里通常表现为两条互相矛盾的日志：

1. 一条是业务自定义的「获取 XX 失败」（打了空对象，看不出原因）
2. 紧接着一条 `IndexOutOfBoundsException` / `NullPointerException`（真正炸的地方）

两条日志往往分属不同 errorHash 簇，容易被认为是两个独立问题。

### 7.2 另一类同源问题：只打 `e.getMessage()`

```java
catch (Exception e) {
    log.error("接口调用异常，" + e.getMessage());   // 输出「接口调用异常，null」
}
```

本轮基础设施组已命中该模式：`HisIconServiceImpl` 只打 `e.getMessage()`，产生「接口调用异常，null」× 56，与图标配置 404（55 条）、404 兜底（49 条）构成三条噪音链。

判据：**日志里出现 `null`、`[]`、`{}` 这类空壳输出，基本都是只找了 message 或打错了对象。**

### 7.3 扫描建议

在 ipcare / opcare 的 BLH 层做一次专项扫描，重点看：

- `catch (Exception e)` 后紧跟 `xxx.get(0)`、`xxx.getItems()`、`xxx.stream()` 的方法
- `log.error(..., e.getMessage())` 或 `log.error("...", 某个局部变量)` 的调用点
- `e.printStackTrace()` 的使用点（正式环境堆栈进不了日志）

### 7.4 日志声明的硬要求

| 反例 | 正例 |
|---|---|
| `log.error("获取失败: {}", rtnList)` | `log.error("获取失败 code={}, patientCount={}", code, size, e)` |
| `e.printStackTrace()` | `log.error("...", e)` |
| `log.error("异常", e.getMessage())` | `log.error("异常", e)` |
