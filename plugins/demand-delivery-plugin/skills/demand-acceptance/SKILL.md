# Demand Acceptance

帮助请求（`--help`、查看用法）：先读取[统一帮助协议](../../../../docs/guides/capability-help.md)，按当前定义展示帮助后结束；Overlay 未映射 `docs/` 时先按 `.agents/capability.json` 的 `CapabilityRoot` 定位协议；附带执行参数也不进入业务流程。

主子需求或明确无代码条目先读[代码归属协议](../../../../docs/demand-code-ownership.md)与[v2批次接口](../../references/acceptance-session.md#主子需求及无代码条目-v2)：按 own/parent/none 分流；共享代码由主需求提交一次，parent 分别补日志并引用共享 push，own 子项独立交付，none 按原因跳过。全组通过后才正式交付，完成还须所有成员完成。旧 v1 保留原授权与回执，BOS 恢复及完成判定同样重核实仓，不自动升级 schema。

让用户连续验收，Agent 接收结论并交付。适用已有实现、待人工验收的需求；复用项目验收台账和已确认事实。跨技术栈、跨宿主执行，脚本需要 Node.js >=22.5.0。

## 调用与授权

用户明确调用 `demand-acceptance` 开展验收交付，即授权当前已确定需求/批次的通过项在既定来源与目标范围内完成必要合入、实仓提交、BOS 代码更新日志及目标分支推送；非 BOS 项目跳过日志阶段。同一批次持续复用该授权，无需交付开关或再次选择范围，逐号“验收通过”后直接交付。用户明确“先登记、暂不交付”等限制时按其要求执行，恢复交付沿用用户的明确指令。真实调用原话与 Agent 解析出的范围分开保存，不将自行推断的“不合回目标”写成用户授权。

仅查看或维护技能、查询验收汇总，以及 Agent 自动加载技能，不产生交付授权；尚未授权时，单独“验收通过”只登记结论。接续时保留真实调用原话、已确认范围和限制，旧批次不自动扩大授权；缺少授权只补问一次，目标不清只澄清缺项。调用不包含部署、删除 worktree 或扩大需求/仓库范围，宿主权限限制和原有执行门禁仍须遵守。

## 接续与接收

### 代码来源

技能参数由 Agent 解释，不传给 `acceptance-session.js`。`-worktree` 是 `--worktree` 的兼容别名；`--pass` 的结论接收见下一节，可与来源参数组合。

| 调用 | 来源与处理 |
|---|---|
| `demand-acceptance` | 默认从当前工作区及既有上下文定位修改；最终交付目标单独核实，来源为 worktree 时仍须取得实仓 commit |
| `demand-acceptance --worktree` | 从已有上下文核实来源 worktree、需求范围和目标仓库，再按需合入和交付 |
| `demand-acceptance --worktree <路径>` | 明确指定来源 worktree；路径含空格时加引号，相对路径按调用时工作目录解析 |

自然语言明确要求从 worktree 接收变更时走同一路径，无需补写参数。`--worktree` 只选择来源，省略它不跳过达到既定交付目标所需的合入。目标来自项目约定或当前对话已确认事实，不从当前修复分支推定；缺失时先澄清目标，保留人工结论及来源证据。接续既有批次时复用已确认的来源与目标，省略参数不重置映射；参数或自然语言与既有映射冲突时，先澄清受影响条目，保留原回执。

跨 worktree 路径先核对来源实际存在、Git common-dir/Overlay 归属、需求对应差异及目标仓库和分支；多个来源按需求逐一映射。裸参数无法唯一定位、目标不明确或出现未知参数时，说明缺项并暂停依赖该信息的合入，不猜测路径或分支；其他已确认条目继续。记录本次来源方式、实际来源及目标，供交接与报告复用。

`--worktree` 只选择代码来源；交付授权按“调用与授权”处理。合入沿用已确认的目标和操作范围，不因选择来源改变验收标准或扩大写入。

### 接收结论

`--pass [需求号列表]` 表达用户对指定需求的人工验收通过，等同于逐号说“验收通过”。已进入本技能的验收会话可直接发送 `--pass` 和列表，无需重复技能名。推荐保留“编号＋标题”供双重核对，也兼容纯编号与同一行逗号分隔的编号。多行粘贴示例：

```text
/demand-acceptance --pass
123 示例需求标题
124 另一条示例需求标题
```

- 多行列表取每个非空行行首的完整数字需求号；行首缩进允许，号与标题以空白分隔，标题可省略或原样保留，标题中的数字不作为其他需求号。同一行纯编号列表使用半角逗号分隔，按编号去重；保留用户原话，不要求重排成固定格式。
- 显式编号先按号定位既有需求/批次，再用所附标题核对同一需求及来源映射；纯编号依赖已确认的上下文。标题不一致或无法确认、同号附有冲突标题、编号缺失/越界或行格式无法识别时，暂停并只澄清相关条目；保留原话，不用标题改配其他编号，也不静默扩批或忽略输入。其他已确认项继续。
- 裸 `--pass` 只在当前工程和上下文能唯一定位一个待验收需求时使用；有多个候选时仅澄清编号，不推断整批通过。
- 对有效条目保存真实原话并登记人工 `passed`；已有相同通过结论时复用回执，从首个未完成阶段续接，已完整交付只报告结果。与既有未通过/暂缓结论矛盾时按原接收规则澄清，不覆盖已开始交付的记录。
- 交付沿“调用与授权”和“逐号交付”；`--pass` 不解除已明确的暂停，不跳过主子分组、差异、验证或提交门禁。使用批次索引时逐号调用现有 `decide`，不新增状态或把此参数传给脚本。帮助、用法咨询及讨论示例仍只读，`--help --pass` 只展示帮助。

1. 确认当前工程、需求与来源映射、台账写入者、提交规范及有效授权。只读当前需求和变化处；稳定的交接资料、BOS 正文、来源提交与验证证据复用。正式编排任务继续使用原 run 和生命周期。
2. 用户报“编号＋通过/未通过/暂缓”时，立即登记编号、原话、结论和时间。上一条交付未结束仍接收下一条；通过且可交付时回复“编号：已登记，排队交付”，其余按实际结论与暂停状态简报。若编号不清或与既有结论矛盾，只澄清该条，其他已确认条目继续。
3. 分开记录自动验证、人工结论、commit、BOS、push。自动通过不代替人工通过；困难的人工补验逐号列明缺口。用户已确认的人工场景无需为交付重复完整测试。

普通单需求可复用已有台账；明确批次使用 [批次协议](../../references/acceptance-session.md) 的 `acceptance-session.js` 管理交付回执与完成判定，不替代正式任务编排或执行 Git/BOS。已有自定义台账保留为取证与恢复资料，将核实的映射和回执接入标准状态流，不能依据自写 `complete` 宣告交付完成。

## 逐号交付

先核对代码归属：none记录原因并跳过代码阶段；parent执行inherit并分别处理日志，提交/push引用主需求的实仓结果；仅own执行下方Git动作。parent没有独立提交仍属有代码交付，不能转none；本轮未新增但存在相关历史提交同样先核实实仓。混合组按[代码归属协议](../../../../docs/demand-code-ownership.md)处理。选用 BOS 日志阶段前，按[可用性依赖协议](../../../../docs/plugin-availability.md)检查阶段依赖，再读取[实仓 commit 门禁](../../../bos-plugin/references/code-update-log.md#实仓-commit-门禁)。

1. 复用“调用与授权”确定的批次授权及目标，传递给 demand-commit、bos-code-update-log 和 push 阶段；各阶段核对精确文件、repo/hash 与远端分支，不重新索取已具备的授权。依赖、配置或权限缺口只阻塞受影响阶段，完成独立可做的准备并说明具体缺项。
2. 每条需求确定一名交付者。检查文件所属仓库与 worktree；不同活动 Git 写入者使用独立 worktree。同一目标仓库/分支的 commit→push 发布段串行，交付者开始该段前取得唯一发布权；全部约定 Git 动作成功后立即释放发布权和 worktree 写入占有，BOS 补录保留原交付者与来源证据，下一条可继续。若分仓并行，跨仓需求按完整仓库集合统一安排，避免部分占有造成等待。
3. 按已确认来源与实仓目标核对需求差异；worktree 变更按需求补丁/片段合入。同一需求的多个来源按目标仓库形成完整变更，共享文件隔离未通过需求片段；无法隔离时暂停相关组。冲突或实质变化补充受影响验证，需人工补验时暂停该条。再调用 [demand-commit](../demand-commit/SKILL.md) 在实仓生成计划并执行已授权提交；已有有效实仓提交按等价证据核实后复用，不重复提交。阶段 worktree commit 只作来源及恢复点，不登记为最终交付 commit。记录全部目标仓库的真实 root/ref/完整 hash 后才进入下一步。
4. 默认先由代码归属者推送一次，独立核对既定远端目标包含本次实仓提交并保存回执；parent 引用共享 push，own 子项独立交付。随后 BOS 项目仅用已保存的实仓 repo/ref/hash 调用 `bos-code-update-log`，parent 分别按自身编号补日志。已有日志先于 push 的批次仍可续接。BOS 依赖、配置、权限、失败或 running/unknown 仅暂停日志；主子日志均不作为 commit、push 或下一条 Git 发布的前置条件。非 BOS 项目跳过日志阶段。
5. 每阶段成功即保存回执，独立推进尚可执行的阶段。部分仓失败保留已成功仓；BOS 超时/未知先只读核对，不能盲目重提。push 失败只恢复未成功目标；远端前进时定向检查与按授权整合，保留已登记的业务 hash，不能为补日志重做或重写提交。中断后先核对已有回执，再续接可执行的未完成阶段；BOS 待补记录保留精确选择、原状态、失败/未知证据和恢复条件，不空转等待或阻塞后续需求。

单号完整交付以全部适用阶段的真实成功回执为准：own 在 BOS 项目须实仓 commit、BOS 和目标 push 均成功；parent 须主实仓提交和 push 引用有效且自身 BOS 成功；none 须人工通过、三代码阶段明确不适用且原因保留。整组完成还须所有主子项完成，JSON 汇总的 groupCompletion 单独计算组状态。非 BOS 项目按自身适用阶段判定。报告区分人工通过、worktree 恢复提交、实仓提交、逐项 BOS 和目标 push；Git 已完成但日志未完成时明确写“代码已推送，BOS 待补”及具体状态，不报告完整交付。仅登记或推送修复分支不能报告完整交付。

## 报告与提效

用户继续验收时保持接收；报告整理不作为下条交付的前置条件。若已授权并行 Agent，可让报告者只读台账/回执并写独立报告，主交付者维护状态；同一文件指定唯一写入者。无并行能力时在阶段间增量汇总，无需为此创建新聊天或索取额外授权。

记录实际测得的准备、commit、BOS、push 耗时；工具外间隔标为未归因。根据积压暂停新需求开发或减少发布并行，优先返修和已通过项的交付。单次宿主/模型的体验不推广为普遍性能结论。

## 编号汇总契约

处理报告固定包含“本批全部需求号汇总”，先写“本批处理需求共 **N 条**”，再按下述格式给出独立 `text` 代码块。以本批已确认的全部需求为集合，包含基线已满足、无需新增代码及仍待处理的需求；不能只从代码差异、提交或交付回执取号。“有代码”“已交付”“待处理”等分组可另列，不能替代全部汇总。输出前逐号核对原始批次，确认去重后的数量与完整集合一致；全部汇总不表示全部已交付。

用户问“验收通过的需求号”输出人工通过项；问“完成/已交付”按约定交付回执汇总。两者不同则分列，不能把自动通过、排队或已 commit 当成完整交付。

每组先给数量，下面一个 `text` 代码块：编号按数值升序、去重、单行、半角逗号分隔、无空格。块内只有需求号，可直接粘贴到 BOS 多需求号查询；标题、数量、状态与说明放在块外。零条写“暂无”，不给空块或占位编号。

示例（仅格式，不代表实际验收）：

本批全部需求号汇总

本批处理需求共 **3 条**：

```text
123,124,136
```

请求人工验收报告时，按[测试协议的结果与交接](../../../../agents/_shared/testing-protocol.md#结果与交接)分别统计功能验证、人工补验和用户验收结论，按号列出对应证据、来源、目标仓库提交、BOS/push 状态及未完成项；排队登记可先于后台交付，最终报告在相应状态变化后增量更新。
