# Demand Acceptance

让用户连续验收，Agent 接收结论并交付。适用已有实现、待人工验收的需求；复用项目验收台账和已确认事实。跨技术栈、跨宿主执行，脚本需要 Node.js >=22.5.0。

## 接续与接收

### 代码来源

以下是由 Agent 解释的技能调用参数，不传给 `acceptance-session.js`。`-worktree` 是 `--worktree` 的兼容别名。

| 调用 | 来源与处理 |
|---|---|
| `demand-acceptance` | 新任务默认验收当前工作区修改，不额外跨 worktree 合入 |
| `demand-acceptance --worktree` | 从已有上下文核实来源 worktree、需求范围和目标仓库，再按需合入和交付 |
| `demand-acceptance --worktree <路径>` | 明确指定来源 worktree；路径含空格时加引号，相对路径按调用时工作目录解析 |

自然语言明确要求从 worktree 接收变更时走同一路径，无需补写参数。当前工作区本身属于 worktree，不构成合回其他仓库的指令。接续既有批次时复用已确认的来源与目标，省略参数不重置映射；参数或自然语言与既有映射冲突时，先澄清受影响条目，保留原回执。

跨 worktree 路径先核对来源实际存在、Git common-dir/Overlay 归属、需求对应差异及目标仓库和分支；多个来源按需求逐一映射。裸参数无法唯一定位、目标不明确或出现未知参数时，说明缺项并暂停依赖该信息的合入，不猜测路径或分支；其他已确认条目继续。记录本次来源方式、实际来源及目标，供交接与报告复用。

参数只选择代码来源，不改变验收标准，也不授予 commit、BOS、push、部署或删除 worktree 的权限。合入沿用已确认的目标和操作范围，不能因选择来源而扩大写入。

### 接收结论

1. 确认当前工程、需求与来源映射、台账写入者、提交规范及有效授权。只读当前需求和变化处；稳定的交接资料、BOS 正文、来源提交与验证证据复用。正式编排任务继续使用原 run 和生命周期。
2. 用户报“编号＋通过/未通过/暂缓”时，立即登记编号、原话、结论和时间。上一条交付未结束仍接收下一条；回复“编号：已登记，排队交付”即可。若编号不清或与既有结论矛盾，只澄清该条，其他已确认条目继续。
3. 分开记录自动验证、人工结论、commit、BOS、push。自动通过不代替人工通过；困难的人工补验逐号列明缺口。用户已确认的人工场景无需为交付重复完整测试。

优先使用已有台账，不为普通单需求新建会话。明确批次且需要断点/多执行者协调时，使用 [批次协议](../../references/acceptance-session.md) 的 `acceptance-session.js`；它只管理验收索引与交付回执，不替代任务编排或执行 Git/BOS。

## 逐号交付

选用 BOS 日志阶段前，按[可用性依赖协议](../../../../docs/plugin-availability.md)检查 demand-delivery-plugin 的 bos-code-update-log 阶段，再核对目标技能的接入与配置要求。

1. 提交、BOS 写入和 push 分别核对本对话已有授权及目标。已授权“这些需求验收后 commit＋BOS＋push”时，复用到该范围内的通过项，直接执行；单独“验收通过”只产生验收结论。缺少某项授权则先完成独立可做的准备，说明精确缺项；权限限制仍由宿主执行。
2. 每条需求确定一名交付者。检查文件所属仓库与 worktree；不同写入者使用独立 worktree。同一目标仓库/分支的 commit→BOS→push 发布段串行，交付者开始该段前取得唯一发布权；其他执行者可只读准备下一条。若分仓并行，跨仓需求按完整仓库集合统一安排，避免部分占有造成等待。
3. 当前工作区路径直接核对需求差异；跨 worktree 路径按已确认来源与目标，以需求补丁/片段合入。同一需求的多个来源按目标仓库合并为一次完整变更；共享文件隔离未通过需求的片段。核对最终 diff 与验收范围；冲突解决或实质变化须补充受影响验证，原人工结论不能自动覆盖变化后的行为，需要人工补验时暂停该条交付。再调用 [demand-commit](../demand-commit/SKILL.md) 生成计划并执行已授权提交，保持既有 pull、HEAD、hook、精确文件与验证门禁。
4. 所有仓库提交 verified 后，BOS 项目复用最终结果中的精确 repo/hash 调用可用的 `bos-code-update-log`；该技能属于 bos-plugin，只有选用 BOS 步骤时才需要已接入。确认成功后再执行已授权 push，并独立核对目标分支包含本次业务提交。非 BOS 项目沿用已约定的交付动作。
5. 每阶段成功即保存回执。部分仓失败保留已成功仓；BOS 超时/未知先核对，不能盲目重提。push 失败只恢复 push；远端前进时定向检查与按授权整合，保留已登记的业务 hash，不能为方便重写已录 BOS 的提交。中断后从首个未完成阶段续接。

单号完成以约定动作的真实回执为准。commit-only 标为“已完成约定交付”；只有 commit、BOS 和 push 均成功才称“已完整交付”。普通成功仅简报编号与交付状态；异常说明失败阶段、保留成果和恢复条件。

## 报告与提效

用户继续验收时保持接收；报告整理不作为下条交付的前置条件。若已授权并行 Agent，可让报告者只读台账/回执并写独立报告，主交付者维护状态；同一文件指定唯一写入者。无并行能力时在阶段间增量汇总，无需为此创建新聊天或索取额外授权。

记录实际测得的准备、commit、BOS、push 耗时；工具外间隔标为未归因。根据积压暂停新需求开发或减少发布并行，优先返修和已通过项的交付。单次宿主/模型的体验不推广为普遍性能结论。

## 编号汇总契约

用户问“验收通过的需求号”输出人工通过项；问“完成/已交付”按约定交付回执汇总。两者不同则分列，不能把自动通过、排队或已 commit 当成完整交付。

每组先给数量，下面一个 `text` 代码块：编号按数值升序、去重、单行、半角逗号分隔、无空格。块内只有需求号，可直接粘贴到 BOS 多需求号查询；标题、数量、状态与说明放在块外。零条写“暂无”，不给空块或占位编号。

示例（仅格式，不代表实际验收）：

验收通过共 **3 条**：

```text
123,124,136
```

请求人工验收报告时，按号列出自动证据、人工补验原因与结论、来源、目标仓库提交、BOS/push 状态及未完成项；排队登记可先于后台交付，最终报告在相应状态变化后增量更新。
