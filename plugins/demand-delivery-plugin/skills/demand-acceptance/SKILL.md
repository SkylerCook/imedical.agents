# Demand Acceptance

帮助请求（`--help`、查看用法）：先读取[统一帮助协议](../../../../docs/guides/capability-help.md)，按当前定义展示帮助后结束；Overlay 未映射 `docs/` 时先按 `.agents/capability.json` 的 `CapabilityRoot` 定位协议；附带执行参数也不进入业务流程。

主子需求或明确无代码条目先读[代码归属协议](../../../../docs/demand-code-ownership.md)与[v2批次接口](../../references/acceptance-session.md#主子需求及无代码条目-v2)：全部关联子项通过后主需求提交一次，子项引用提交并分别补日志，全部日志确认后共享push一次；none按原因标记阶段不适用。旧v1批次保留原契约，不自动升级。

让用户连续验收，Agent 接收结论并交付。适用已有实现、待人工验收的需求；复用项目验收台账和已确认事实。跨技术栈、跨宿主执行，脚本需要 Node.js >=22.5.0。

## 调用与授权

用户明确调用 `demand-acceptance` 开展验收交付，即授权当前已确定需求/批次的通过项依次提交、补 BOS 代码更新日志并推送；非 BOS 项目跳过日志阶段。同一批次持续复用该授权，无需交付开关或再次选择范围，逐号“验收通过”后直接交付。用户明确“先登记、暂不交付”等限制时按其要求执行，恢复交付沿用用户的明确指令。

仅查看或维护技能、查询验收汇总，以及 Agent 自动加载技能，不产生交付授权；尚未授权时，单独“验收通过”只登记结论。接续时保留真实调用原话、已确认范围和限制，旧批次不自动扩大授权；缺少授权只补问一次，目标不清只澄清缺项。调用不包含部署、删除 worktree 或扩大需求/仓库范围，宿主权限限制和原有执行门禁仍须遵守。

## 接续与接收

### 代码来源

以下是由 Agent 解释的技能调用参数，不传给 `acceptance-session.js`。`-worktree` 是 `--worktree` 的兼容别名。

| 调用 | 来源与处理 |
|---|---|
| `demand-acceptance` | 新任务默认验收当前工作区修改，不额外跨 worktree 合入 |
| `demand-acceptance --worktree` | 从已有上下文核实来源 worktree、需求范围和目标仓库，再按需合入和交付 |
| `demand-acceptance --worktree <路径>` | 明确指定来源 worktree；路径含空格时加引号，相对路径按调用时工作目录解析 |

自然语言明确要求从 worktree 接收变更时走同一路径，无需补写参数。当前工作区本身属于 worktree，不构成合回其他仓库的指令。接续既有批次时复用已确认的来源与目标，省略参数不重置映射；参数或自然语言与既有映射冲突时，先澄清受影响条目，保留原回执。

跨 worktree 路径先核对来源实际存在、Git common-dir/Overlay 归属、需求对应差异及目标仓库和分支；多个来源按需求逐一映射。裸参数无法唯一定位、目标不明确或出现未知参数时，说明缺项并暂停依赖该信息的合入，不猜测路径或分支；其他已确认条目继续。记录本次来源方式、实际来源及目标，供交接与报告复用。

`--worktree` 只选择代码来源；交付授权按“调用与授权”处理。合入沿用已确认的目标和操作范围，不因选择来源改变验收标准或扩大写入。

### 接收结论

1. 确认当前工程、需求与来源映射、台账写入者、提交规范及有效授权。只读当前需求和变化处；稳定的交接资料、BOS 正文、来源提交与验证证据复用。正式编排任务继续使用原 run 和生命周期。
2. 用户报“编号＋通过/未通过/暂缓”时，立即登记编号、原话、结论和时间。上一条交付未结束仍接收下一条；通过且可交付时回复“编号：已登记，排队交付”，其余按实际结论与暂停状态简报。若编号不清或与既有结论矛盾，只澄清该条，其他已确认条目继续。
3. 分开记录自动验证、人工结论、commit、BOS、push。自动通过不代替人工通过；困难的人工补验逐号列明缺口。用户已确认的人工场景无需为交付重复完整测试。

优先使用已有台账，不为普通单需求新建会话。明确批次且需要断点/多执行者协调时，使用 [批次协议](../../references/acceptance-session.md) 的 `acceptance-session.js`；它只管理验收索引与交付回执，不替代任务编排或执行 Git/BOS。

## 逐号交付

先核对代码归属：none记录原因并跳过代码阶段；parent执行inherit并分别处理日志，提交/push引用主需求结果；仅own执行下方Git动作。选用 BOS 日志阶段前，按[可用性依赖协议](../../../../docs/plugin-availability.md)检查 demand-delivery-plugin 的 bos-code-update-log 阶段，再核对目标技能的接入与配置要求。

1. 复用“调用与授权”确定的批次授权及目标，传递给 demand-commit、bos-code-update-log 和 push 阶段；各阶段核对精确文件、repo/hash 与远端分支，不重新索取已具备的授权。依赖、配置或权限缺口只阻塞受影响阶段，完成独立可做的准备并说明具体缺项。
2. 每条需求确定一名交付者。检查文件所属仓库与 worktree；不同写入者使用独立 worktree。同一目标仓库/分支的 commit→BOS→push 发布段串行，交付者开始该段前取得唯一发布权；其他执行者可只读准备下一条。若分仓并行，跨仓需求按完整仓库集合统一安排，避免部分占有造成等待。
3. 当前工作区路径直接核对需求差异；跨 worktree 路径按已确认来源与目标，以需求补丁/片段合入。同一需求的多个来源按目标仓库合并为一次完整变更；共享文件隔离未通过需求的片段。核对最终 diff 与验收范围；冲突解决或实质变化须补充受影响验证，原人工结论不能自动覆盖变化后的行为，需要人工补验时暂停该条交付。再调用 [demand-commit](../demand-commit/SKILL.md) 生成计划并执行已授权提交，按其同步复核协议处理上游前进后的自动接续，保持 hook、精确文件与现场验证门禁。
4. 代码来源完成校验（自身提交或已引用verified主提交）后，BOS 项目复用最终结果中的精确 repo/hash 调用可用的 `bos-code-update-log`；该技能属于 bos-plugin，只有选用 BOS 步骤时才需要已接入。确认全部适用主子日志成功后，仅由代码归属者执行已授权push，并独立核对目标分支包含本次业务提交；子项引用该回执。非 BOS 项目沿用已约定的交付动作。
5. 每阶段成功即保存回执。部分仓失败保留已成功仓；BOS 超时/未知先核对，不能盲目重提。push 失败只恢复 push；远端前进时定向检查与按授权整合，保留已登记的业务 hash，不能为方便重写已录 BOS 的提交。中断后从首个未完成阶段续接。

单号完整交付以全部适用阶段的真实成功回执为准：own在BOS项目须commit、BOS和push均成功；parent须主提交和push引用有效且自身BOS成功；none须人工通过、三代码阶段明确不适用且原因保留。非BOS项目按自身适用阶段判定。仅登记、已提交或交付暂停均不能标为完整交付。普通成功仅简报编号与交付状态；异常说明失败阶段、保留成果和恢复条件。

## 报告与提效

用户继续验收时保持接收；报告整理不作为下条交付的前置条件。若已授权并行 Agent，可让报告者只读台账/回执并写独立报告，主交付者维护状态；同一文件指定唯一写入者。无并行能力时在阶段间增量汇总，无需为此创建新聊天或索取额外授权。

记录实际测得的准备、commit、BOS、push 耗时；工具外间隔标为未归因。根据积压暂停新需求开发或减少发布并行，优先返修和已通过项的交付。单次宿主/模型的体验不推广为普遍性能结论。

## 编号汇总契约

处理报告固定包含“本批全部需求号汇总”，先写“本批处理需求共 **N 条**”，再按下述格式给出独立 `text` 代码块。以本批已确认的全部需求为集合，包含基线已满足、无需新增代码及仍待处理的需求；不能只从代码差异、提交或交付回执取号。“有代码”“已交付”“待处理”等分组可另列，不能替代全部汇总。输出前逐号核对原始批次，确认去重后的数量与完整集合一致；全部汇总不表示全部已交付。

用户问“验收通过的需求号”输出人工通过项；问“完成/已交付”按约定交付回执汇总。两者不同则分列，不能把自动通过、排队或已 commit 当成完整交付。

每组先给数量，下面一个 `text` 代码块：编号按数值升序、去重、单行、半角逗号分隔、无空格。块内只有需求号，可直接粘贴到 BOS 多需求号查询；标题、数量、状态与说明放在块外。零条写“暂无”，不给空块或占位编号。

示例（仅格式，不代表实际验收）：

本批全部需求号汇总

本批处理需求共 **3 条**：

```text
123,124,136
```

请求人工验收报告时，按[测试协议的结果与交接](../../../../agents/_shared/testing-protocol.md#结果与交接)分别统计功能验证、人工补验和用户验收结论，按号列出对应证据、来源、目标仓库提交、BOS/push 状态及未完成项；排队登记可先于后台交付，最终报告在相应状态变化后增量更新。
