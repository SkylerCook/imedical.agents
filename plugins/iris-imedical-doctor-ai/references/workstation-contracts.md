# 持续演进的 AI 集成框架

## 框架发现先于实现

框架代码、文件拆分和原型都可能变化。每次从目标工程当前入口、资源加载、导出、调用者、测试和相关提交识别能力，明确本次读取的是哪份实现。文件名如 chat.js 只是线索，不代表固定职责；没有同名文件也不表示工程缺少对应能力。

按本次需求核对：

- 对话如何发起、排队、取消，流式响应如何解析与分发。
- 卡片或其它交互组件如何发现、注册、渲染、绑定事件、销毁及加载依赖。
- 患者/就诊/病历上下文如何传递，异步结果如何在切换后失效。
- 业务服务如何校验、确认、执行并反馈结果，哪些调用者共用它。
- 会话与业务结果如何保存和恢复，旧数据兼容由谁负责。

只记录相关事实。动态或跨仓依赖不能解析时说明缺口，不猜测接口。

## 配置驱动的卡片引入

先核实当前加载来源：服务端配置、静态清单或两者组合。工程已改为配置驱动时，沿现有配置入口接入，不再按旧静态文件清单添加卡片，不额外建立一套硬编码加载列表。

按「配置获取 → 当前上下文下的有效项目 → 脚本地址解析及加载 → 执行注册 → 动作分发」检查完整链路。核对现行实现中的启用、授权、表达式等过滤条件及生效范围，不假定配置界面可见就等于当前医生会话能取得并加载。配置项 ID、脚本路径与动作代码是不同角色，按实际映射核对，不要求三者同名。

配置缺失、合法过滤、配置请求失败、资源加载失败与脚本注册失败分别定位；不把请求失败视为空配置，也不通过硬编码补载绕过授权过滤。确认配置缓存与刷新机制后再判断是否需要刷新，不能把清浏览器缓存当作通用修复。

配置分类名、维护菜单、读取接口、链接解析基准及具体项目值仅留目标工程。通用插件不固定这些标识；读取与修改配置按目标工程现有授权边界执行，框架资料更新不授权更改服务器配置。

## 主流程导航与辅助快捷入口

分别核对三类职责及其实际配置来源，不要求工程必须拆成三份配置：

- 卡片加载：哪些脚本被加载并注册，使动作可被分发。
- 主流程导航：哪些步骤对当前上下文可见、如何排序，以及点击如何映射到动作。
- 辅助快捷按钮：补充信息、查询等辅助入口的显示与执行方式，不默认承担主流程导航。

卡片加载配置完成不代表主流程入口已经具备，导航项可见也不证明对应卡片已注册。沿现有映射核对两端；主流程已迁入配置入口时，不为新增卡片向快捷区硬编码重复按钮，也不为满足旧测试恢复已移除的按钮。只有明确需求且现有入口不能满足时，才考虑新增入口。

流程展示顺序、步骤点击行为、业务执行前置校验分别取证。排列在前不等于必须先完成，点击步骤不等于已完成该业务，也不自动获得快捷入口的校验例外。若快捷区本身也由配置生成，继续复用其配置链路，不凭历史 HTML 推断现状。配置名称、步骤数量和动作码仅留目标工程。

## 扩展与框架修改

优先使用当前扩展点。若现有框架不足，可以在授权范围内改进框架；先说明消费者、协议和历史数据影响，再同步调用者与测试。不能以“新增卡片不许改对话代码”等旧约束禁止合理演进，也不能为单个需求无依据地重构全部框架。

卡片动作标识、持久化策略、渲染返回值、事件名和请求字段均取自当前代码/协议。新增策略不因插件未列举就被判为非法。模板仅帮助组织分析，不生成绑定某个基类的业务骨架。

## 验证稳定语义

流式分块、错误与取消、重复操作、异步销毁、患者切换、业务成功反馈、历史恢复和关联视图一致性是检查方向；具体断言依据当次需求及现行接口制定。

业务动作、界面显示和会话记录分别验证。修改请求位置、编码或事件协议时核对双方；修改存储结构时检查旧记录。不要把历史经验里的参数名或枚举变成永久门禁。

## 接入方式与触发边界

- 嵌入：识别宿主生命周期、上下文与业务服务边界，不预设特定布局或组件框架。
- 外挂：识别打开、上下文传递、结果返回与关闭契约，不预设 DLL、浏览器扩展或通信方式。
- 旁路：识别数据来源、触发时机、结果归属及业务写入权限，不预设能够直接保存。

接入方式由当次目标决定；既有样例不是其它模式的实现证明。通用 IRIS 编码、部署与接口能力继续由原 owner 提供。

## 快捷入口与流程门槛

仅当现行工程存在快捷入口或本次需求明确要求新增时应用本节；不要求每张卡片提供快捷按钮。分别确认「何时推荐动作」「能否直接展示卡片」「业务能否执行」。快捷入口是否跳过新增的流程顺序限制由需求明确，不能因此绕过原服务的权限、签名、质控或设备校验；原流程没有硬性门槛时，也不凭原型顺序新增通用禁止条件。

入口来源由可信宿主确定，不从 AI 返回数据读取授权标记。沿实际调用链检查参数是否到达实例及执行层；不假定基类会保留所有自定义选项，也不为传一个选项无依据地修改基类。默认值、历史恢复及直接动作分发不得意外继承快捷入口的例外。例外不固定为某个字段名或枚举。

## 传统页面复用的完整边界

- 抽取前列出实际生效的查询条件、默认选择、分组、配置解析和业务校验；服务返回的默认值不代表旧页面实际采用该值。
- 服务接收显式上下文和选择，UI 管理控件、确认、遮罩及宿主回调。是否拆成 page/service/preview 按现行架构确定，不强制目录或类名。
- 原页面的完成流程、关闭窗口等回调由原调用方保留，不能因卡片复用服务而隐式触发。单类操作使用独立选择，不污染后续全部操作。
- 复用范围包含运行依赖：公共 head、插件控件、预览宿主、iframe API 和就绪时机。页面 load 不代表业务 API 就绪；等待、失败与关闭均须可收尾，等待后重新校验上下文。
- 逐个验证旧页面及新调用者的任务参数和结果语义。接口大小写、传输与返回结构按 coding-iris-plugin 的前端接口契约核对，不另维护领域副本。

## 多宿主与无 Chat 兼容

涉及传统页面、共享服务或跨窗口联动时，先核实目标工程实际支持的宿主布局、入口、窗口关系与既有回调，包含未启用 Chat、未加载卡片或未注册监听的情况。共享业务能力不得以 Chat 全局对象、卡片实例或 AI 资源已加载为前提，也不得为传统入口强制加载 AI 框架。

业务执行结果与 AI 界面刷新分开处理。通知属于可选联动：无接收方时正常结束；通知 API 缺失、监听异常或跨域窗口不可访问时，不中断原业务、不改写已提交结果、不自动重试业务。传统页面原有刷新、关闭及宿主回调按原契约保留，不能因接入卡片而误触发后续诊疗流程。

优先复用宿主已有的事件或回调能力。需要跨窗口时验证同源可达范围和来源，不假定固定 parent/top 层级，不绕过跨域限制，不广播无关患者数据。接收方核对患者或就诊归属及实例存活状态；异步刷新防重复，销毁后清理监听。具体通信机制、事件名和字段由当前工程确定，不统一强制某种实现。

新增筛选、重打或卡片专属行为通过显式选项限定作用范围；旧调用方未提供选项时保持原业务语义。验证应同时覆盖有 Chat 与无 Chat 的实际调用链，不能仅凭异常被捕获就认定多宿主兼容。

## 状态按钮与组合动作

状态决定按钮文案和可用动作时，区分可靠的未完成、已完成、未知及查询失败，不能把失败当作未完成。需要医生点击的动作仅在事件处理阶段触发；初次渲染、状态刷新和历史恢复不自动打开后续卡片或执行业务。业务完成后的状态更新沿宿主现有事件或刷新机制处理，避免长期显示过期动作。

复用现有卡片分发或预览服务前，核实入口、上下文、依赖及销毁契约；预览与提交分别处理，不因进入预览自动执行打印或保存。

组合动作逐步确认操作对象、顺序、前置校验及取消/失败时已经发生的结果。文案准确表达实际效果；切换对象、接诊、呼叫等不互为同义。是否有联动须追踪完整调用链和回调，不能仅凭当前卡片没有直接调用就断言无副作用。视觉调整本身不授权改变业务顺序或新增组合动作。
