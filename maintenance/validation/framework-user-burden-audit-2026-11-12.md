建议优先修正初始化闭环和更新结果判定，再收敛入口文档与配置维护方式。现有工作区解析、配置迁移、薄索引、部署回执、会话管理和验证证据能力足以承接这些改进，采用局部修正即可推进。

1. 让已授权初始化自动完成可确定的配置和索引生成，统一新编码契约，减少用户手填与重复确认。
2. 修复配置不完整时的错误诊断，让用户一次提供必要事实，并让工具保护已有配置。
3. 使更新结果能准确表达必要步骤失败、可选步骤警告及已完成范围，避免调用方把进程结束当作全部完成。

### 1. 初始化指令统一并消除可确定的人工步骤

**发现**

`coding-iris-init` 第 4 步仍要求源码、上传和服务器运行编码统一为 `utf8`，同一技能开头引用的编码契约已经支持源码与服务器分开配置。第 5 步在缺少 `.mcp.json` 时要求用户复制模板填写，并把本机 MCP 路径列入禁止代填范围。第 6 步又要求用户确认后才写薄索引。这些文字可能让 Agent 在已获初始化授权、已有配置事实时仍停下来。规则冲突已确认，实际宿主停顿频次待测。[初始化技能](../../plugins/coding-iris-plugin/skills/coding-iris-init/SKILL.md)、[编码契约](../../plugins/coding-iris-plugin/references/frontend-encoding.md)

**执行方案**

- 初始化只保留编码契约的条件路由，字段和首次确认规则统一引用 owner 文档。明确源码编码、目标编码、确认状态的区别。
- 在有效初始化授权内，由 Agent 创建缺失实例文件并调用既有脚本。已有合法值直接复用，必需且不可推导的业务事实集中询问。
- 本机运行时路径通过 CapabilityRoot、平台和文件存在性确定，保留显式 custom 配置。连接身份、目标环境和业务编码决定继续依据明确事实处理。
- 将薄索引 DryRun 用于内部差异检查。授权已覆盖且只有可识别生成物时直接 Write，发现自定义冲突时提出具体问题。
- 初次接入、已有工程补缺、Overlay、纯后端和 offline 共用条件分流。先利用 `source-sync configure`、既有迁移器与生成器完成闭环，出现真实重复编排后再决定是否提取函数。

**验收与部署**

在上述五类工程夹具验证初始化后目标技能可发现、配置 Check 与所选能力一致、重复执行幂等。增加“源码 UTF-8／服务器 GBK”的合法样本，确认初始化不会覆盖已有目标编码。已知事实齐备的初始化样本应无额外确认，未知事实集中一次收集。coding 插件按版本治理发布，已有 enabled 工程通过普通更新刷新规则和索引，私有编码决定继续保留。

**收益与成本**

预期减少复制模板、寻找可执行文件和确认索引三类操作。成本集中在条件分支核对与初始化测试，用户无需新增日常配置。

### 2. 配置生成器先校验、集中诊断、复用既有值

**发现与复现**

`sync-env-config.js` 解构配置后立即访问 `iris.scheme`，随后才执行 `requireValue`。当前源码在两个隔离输入下得到以下结果。

| 输入 | 本轮结果 |
|---|---|
| `{}` | `TypeError: Cannot read properties of undefined (reading 'scheme')`，没有字段诊断 |
| `{"iris":{}}` | 返回首个缺失字段 `iris.host` 后退出 |

该试验确认缺少整个配置段时诊断失效，以及现有校验逐项退出的行为。读取被替换为内存数据，结论限于该脚本分支。[生成器](../../plugins/coding-iris-plugin/scripts/iris-tools/sync-env-config.js)

**执行方案**

- 先验证顶层及 section 类型，再计算默认值。一次输出当前选定能力所需的全部缺失字段，日志只包含字段名和修复动作。
- 对缺文件、非法 JSON、错误类型、未填占位值分别返回可执行诊断。SFTP 禁用时跳过其必填校验。
- 沿现有优先级读取 `.mcp.json` 与 `project-env.json`，明确本次变更字段。已有连接优先复用，必要冲突一次展示。
- 继续复用 `iris-session-migration.writeGenerated` 的受管入口保护、私有文件忽略检查和并发保护。先验证同名 MCP 服务的扩展字段保留，再决定是否调整合并逻辑。

**验收与部署**

扩展现有 workspace/config 测试，覆盖空对象、null、错误 section 类型、缺多字段、SFTP 禁用、已有受管入口、其它 MCP、显式禁用、重复执行及中途失败。最终用正式 CLI 从隔离工程完成生成，再通过运行时配置读取验证实际生效值。失败时已有文件应保持一致，测试仅使用虚构连接。[现有工作区测试](../../scripts/tests/iris-workspace-context.tests.js)、[配置写入实现](../../scripts/lib/iris-session-migration.js)

随 coding 插件更新分发。修复允许读取旧格式，日常使用无需迁移配置文件位置。预计减少多轮补字段和裸堆栈排查，具体耗时由第 7 项记录。

### 3. 更新结果与必要步骤失败一致

**发现**

`Invoke-PluginConfigMigrations` 捕获缺脚本和执行异常，转为 `config-migration-failed`。该状态进入 `Action required` 输出。脚本末尾显式失败检查覆盖 adapter、thin-index、skill owner 冲突，未包含配置迁移失败。前面的 `Test-UpdateBlocked` 检查发生在插件迁移之前。因此，存在“必要迁移失败已报告，但总体缺乏对应失败判定”的源码缺口。整体子进程退出码仍需故障注入确认，不能将这项静态发现写成已复现现场误报。[更新器](../../scripts/update-agents.ps1)

**执行方案**

- 在原有结果汇总位置统一判定必要步骤的完成状态，沿用 status、plugin、phase 和 reason。
- 针对当前启用插件的必要配置迁移失败，返回非成功并列出受影响能力、已完成步骤和可重试入口。
- 可选目录导航维护失败继续输出警告。现有测试已明确要求该情况不阻断框架更新，应保留该行为。
- 重试复用原迁移器幂等逻辑，保留已完成结果。先通过现有调用上下文确定必要性，只有确实无法表达时才评估新增 manifest 字段。

**验收与部署**

在现有更新器测试中注入缺迁移脚本、迁移非零、非法输出及可选 docs 失败。分别断言退出码、摘要、受影响插件和第二次执行结果。覆盖新安装、旧项目更新及 Overlay 刷新，并在 Windows PowerShell 5.1 和 7 验证。同步调用方对退出码的处理，避免把“部分完成”误判为全部回滚。[更新器测试](../../scripts/tests/update-agents.tests.ps1)

通过根脚本正常更新分发，旧更新器自更新路径一并回归。收益是让完成判定可靠，成本是失败分类与调用方兼容核对。

### 4. 将更新的只读检查与授权更新入口写清楚

**发现**

standard 模式的普通 `DryRun` 会执行 fetch、可能的快进 pull 和 sparse 刷新。文档对此已有解释，但默认操作仍是 DryRun 后 Write。只读检查实际应使用 `Check` 或 `DryRun -NoPull`。该设计有兼容价值，也增加理解成本；尚无实测数据证明重复网络检查是主要耗时。[更新说明](../../docs/update-agents.md)、[更新器](../../scripts/update-agents.ps1)

**执行方案**

- 在快速入口按用户目的给出“检查当前副本”“执行已授权更新”“预演生成层差异”三种现有命令，清楚标注 capability 是否变化。
- 普通已授权更新评估直接使用 Write 的完整保护链。先验证与当前两步路径的差异、冲突展示和自更新行为，再调整推荐流程。
- 保留旧 DryRun 语义和脚本兼容。Overlay 继续共享能力包更新一次、各 ContextRoot 本地刷新。
- 不引入额外更新批准文件或长驻任务状态。所需摘要从已有 results 生成。

**验收与部署**

核对只读模式文件摘要与 Git HEAD 均不变化。比较已授权 Write 与两步路径的最终生成物，覆盖 dirty、ahead、diverged、旧 sparse、自更新重启和 Overlay。确认单次路径达到同等保护后更新 runbook。若最终仅调整文档，按文档影响面验证即可。

|---|---|---|
| 根 README | 724 | 40,332 |
| 维护记忆入口 | 91 | 9,878 |
| backlog | 249 | 25,035 |
| 更新 runbook | 967 | 62,773 |

维护记忆入口要求约两分钟可读完，但包含多轮实现和验证细节。当前入口仍同时出现 TLS 缺省 false 与普通 HTTPS 默认验证证书的表述，需结合历史适用范围阅读才能消解。初始化编码旧表述也体现了多处维护同一事实的风险。[维护入口](../../memory/agent-kit-maintenance-memory.md)、[长期决策](../../memory/agent-kit-maintenance-decisions.md)、[更新说明](../../docs/update-agents.md)

**执行方案**

- 维护入口只保留首要原则链接、当前少量重点和任务路由。完成证据归维护日志，稳定契约归 owner 文档。
- 根 README 保留用途、安装、能力导航与主要边界。长篇版本演进转为已有维护日志或发布记录链接。
- runbook 首屏给当前更新路径和失败恢复入口，版本迁移按适用条件按需读取。旧版本仍需要的操作说明继续随项目分发。
- backlog 将同一事项的重复状态合并到已有主项，每项保留优先级、下一步、启动条件和完成标准。已完成部分迁入日志。
- 逐段处理 TLS、编码、vendor v3/v4 等历史内容，注明历史版本或删除已失效的现行口吻。

**验收与部署**

抽查新接手 Agent 能否通过入口找到初始化、普通部署和更新恢复的唯一现行说明；统计必要读取和重复结论。复用文档链接测试并核对旧链接。涉及 docs 文件移动时按现有文档布局迁移，插件内文档遵循 owner 版本治理。本文提出的体量压缩目标由阅读试验决定，避免增加字符数提交门禁。

发布沿现有插件分发和 enabled 状态管理。只有真实任务需要的插件进入本批实施，用户日常操作无需增加全插件扫描。

### 7. 用完整用户路径验收减负收益

当前维护记录包含大量单元测试与单目标实测，backlog 也保留真实宿主调用和前后效率对照。建议复用这些入口，为前六项的实施补一份短对照记录，使用既有维护日志承载。

| 用户路径 | 验证结果 | 记录成本 |
|---|---|---|
| 已知事实齐备的新项目初始化 | 所选能力可发现且实际配置可读 | 用户确认次数、手工编辑文件数 |
| 已有工程正常更新 | 私有值保持、必要迁移完成、重复执行幂等 | 命令次数、人工恢复步骤 |
| 明确目标和文件的普通部署 | 上传、回读及所需编译通过 | 重复读取、重复预检、总耗时 |
| 可确定未发出的连接失败 | 在现有预算内恢复或给出准确停止原因 | 用户介入次数、恢复耗时 |
| 已派发但结果未知的写入 | 对应范围受保护，可依据真实结果恢复 | 误重放数、无关任务被阻断情况 |

优先用相同项目夹具、相同宿主和相同任务比较前后结果，初轮至少各取一个正常及一个失败样本。少量样本只作方向性证据。可靠性底线是保留用户配置、范围授权、冲突保护与结果核实；效率指标从实际记录比较，不预填“提升百分比”。

真实医院验证沿目标项目授权执行。跨平台验证按受影响实现与已有决定安排，当前已暂缓事项保持原队列。会话初次连接恢复和资源释放沿既有 P1 后续验收，取证后再决定是否调整恢复策略。[现有队列](../../memory/agent-kit-maintenance-backlog.md)

## 建议实施批次

### 第一批，完成初始化与更新结果修正

执行第 1–3 项。先补失败用例，再修改指令与实现，最后通过新建、已有、迁移和 Overlay 的完整入口验收。预计 3–6 个有效工作日，插件版本及相关测试按每个完整变更目的同步。

交付范围包括 coding 初始化与生成器修复、必要更新失败判定、定向回归和升级说明。先在隔离夹具验证，再在获授权的一个真实项目更新并执行所选默认任务。若只有文件生成成功，验收继续保持未完成。

### 第二批，收敛日常操作和文档

执行第 4–5 项，并使用第 7 项记录对照。先明确现行流程，再搬移历史解释，逐项核对链接和真实读取路径。预计 1.5–3 个有效工作日。

### 第三批，按需求接入剩余能力

执行第 6 项，并沿现有 P1 队列补会话故障恢复与部署试点。每个插件单独确认依赖和外部操作范围，完成一条真实使用路径后再推广。

## 部署与恢复安排

1. 在实际实施时重新核对 HEAD、工作区状态和 owner 版本，避免复用本文快照覆盖后续修改。
2. coding 插件变更按 SemVer 与不可变发布记录要求处理。根更新器及 docs 变化按各自影响面验证，提交前运行适用的版本校验。
3. 发布后 standard 项目使用原更新器取得完整能力包，Overlay 先更新共享 CapabilityRoot，再刷新各 ContextRoot。验证生成物及实际宿主发现。
4. 配置补缺与迁移保留自定义值，修改前后核对精确范围。依赖变更按现有 manifest 和 vendor 分发，避免要求业务工程额外安装框架依赖。
5. 回归时优先停用受影响的新路径并按精确变更恢复。配置格式若发生升级，先核对旧版兼容性及本次修改前内容，避免直接降级覆盖新的私有配置或恢复记录。
6. 更新后的完成报告给出已更新能力、实际验证结果和具体剩余项。普通诊断警告由工具保留，确需用户决定时说明受影响目标及最小动作。

本轮建议采用现有入口和运行时做局部修正。当前证据尚不支持整体重写更新器、统一全部配置文件、增加全局状态服务或重新设计治理框架。
