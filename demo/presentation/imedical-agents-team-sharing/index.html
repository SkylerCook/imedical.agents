04 · 发现机制
Plugin & Thin-Index

能力源完整部署，发现入口保持轻量

Plugin（插件能力包）保存真实能力

rules / skills / references / templates / scripts

.agents/skills/i18n-coding/SKILL.md
→ .agents/plugins/i18n-iris-plugin/skills/i18n-coding/SKILL.md

thin-index 只做浅层路由，不复制完整正文，也不缩减安全约束。

available可发现

能力已拉取；不合并配置、不生成插件 thin-index。

enabled已启用

真实 init（初始化）已闭环；参与更新、配置合并与索引维护。

disabled已停用

默认跳过；历史入口只报告，不擅自删除。

讲者备注

目录存在不等于已经启用，这是最容易误解的地方。plugin_profile.md 才是状态事实来源；enabled 也不是手工改一个词，而是 init 闭环完成后的结果。

05 · 执行模型
Execution Model

角色、流程、SOP 与红线各自负责一件事

Agent谁来负责：角色、职责、输入输出与禁止事项。
Workflow按什么顺序：阶段、交接、并行边界与完成条件。
Skill具体怎么做：可触发、可执行、可复用的 SOP。
Rule哪些不能错：领域约束、安全边界与验证标准。

能力较少时仍可降级

没有 subagent（子 Agent）、没有 skill 发现、甚至不能解析 YAML，也可以直接按 canonical Markdown 串行执行。

retrospective只读复盘
serial单 Agent 串行
multi-agent多 Agent 协作

讲者备注

这四者不是层层套娃。Agent 解决责任归属，Workflow 解决执行秩序，Skill 解决做法，Rule 解决不能违反的边界。

imedical.agents
06 · 部署模型
Deployment

一个项目一份能力，或多个模块共享一份能力

Standard单项目标准部署

  • 业务项目中 `.agents` 是独立 Git 仓库
  • sparse checkout（稀疏检出）只拉取运行所需内容
  • 项目本地 config / memory / rules 保持独立
  • 适合单一业务工程

Workspace Overlay多模块共享能力

  • 多个模块共享 canonical `CapabilityRoot`（能力根）
  • 每个模块保留独立 `ContextRoot`（上下文根）
  • `capability-once / context-many`（能力一份、上下文多份）
  • 通过 manifest（能力清单）、Junction（目录联接）与根边界验证
现场演示 Standard；Overlay 只讲设计，不临时搭建、不触碰真实模块。

讲者备注

Standard 最容易理解，也是今天实演路径。Overlay 解决模块工作区重复能力的问题，但它有严格的路径与 reparse-point 安全边界，不适合临时现场搭建。

[Sources] README.md：多模块 Workspace Overlay；docs/workspace-overlay.md

附录 C
Glossary

术语表：先把抽象名词翻译成职责

Canonical
唯一维护、用于校准其他入口的真实能力源。
Plugin
把规则、Skill、脚本和模板装在一起的领域能力包。
Thin-Index
只负责发现与跳转、不复制完整能力正文的浅层索引。
Agent
面向一类任务的专项角色，明确职责、输入输出与禁区。
Workflow
规定阶段顺序、交接关系和完成条件的执行流程。
Manifest
声明插件能力、依赖与初始化入口的清单文件。
Adapter
把通用能力映射到具体 Agent 工具的适配入口。
Verifier
在最后一次修改后独立核验结果的验证角色。
主要事实来源： README.md · docs/update-agents.md · docs/workspace-overlay.md · agents/i18n-agent/AGENT.md · workflows/i18n-change.workflow.md · plugins/*/.agents-plugin/plugin.json
