# imedical.agents 使用手册（团队版）

`imedical.agents` 把团队的开发规范、常用技能和操作流程交给 AI 开发工具复用。推荐先显式选择对应技能，再用自然语言补充任务要求，让 Agent 按项目约定查资料、改代码、验证和准备交付，减少每次重新解释工程背景与操作步骤的工作。

这份手册面向第一次接触能力包的同事，也提供日常使用的请求示例。**先完成一个小任务，再按需要了解更多能力。** 文中的请求代码块是发给 Agent 的话，不是终端命令；使用前替换方括号中的内容。

## 1. 它能帮你做什么

| 工作场景 | 可以交给 Agent 的工作 | 你需要提供或确认 |
|---|---|---|
| 处理已有 BOS 需求 | 读取需求、分析影响、实施、自查、准备交付 | 需求编号、目标工程、操作范围及验收结果 |
| 修改 IRIS 页面或后端 | 定位代码、按规范修改、运行适用检查 | 页面或类、当前问题、预期效果 |
| 从文档制作治疗表单 | 提取要求、澄清字段、生成表单、预览与验证 | 原始文档、CA/CR 类型及业务歧义 |
| 开发接口或做国际化 | 按阶段整理映射、实施、核验 | 接口规范或需处理的页面、字典范围 |
| 跨会话继续需求 | 保存当前进展、未完成项与接续入口 | 需要交接的任务范围 |

能力是否可执行，取决于当前项目是否完成接入、配置是否齐全，以及工具和环境是否支持。Agent 按既定流程执行可以减少手工遗漏，**最终仍以检查证据和实际验收为准**。

已接入的工程可直接看第 3 节；首次使用从下一节开始。完整能力见[能力目录](capability-catalog.md)，具体场景见[使用指南](capability-guide.md)。

## 2. 第一次使用：完成一个小任务

### 2.1 在业务工程中打开 Agent

打开你要工作的工程目录，让 Agent 能读取项目文件并执行本地命令。不要在能力包源仓里安装业务项目的 `.agents`。

推荐让 Agent 先检查环境，再执行安装。Git、Node.js 和 PowerShell 等前置条件以[安装更新说明](../update-agents.md)为准；Node.js 用于能力包工具链，不是 HIS 业务系统的生产运行依赖。环境缺失时，可能需要你安装软件、登录或完成权限操作。

### 2.2 安装能力包并建立项目上下文

把下面的请求发给 Agent：

```text
按 https://gitee.com/skyler-cook/imedical.agents 的 README 部署 .agents 到当前工程。
先检查环境和现有部署状态；首次安装时将脚本下载到任务临时目录，核对后执行。
已有部署沿对应更新流程处理，非标准目录或冲突先保留现场并报告。
随后使用 project-context-maintenance 初始化或补齐项目上下文，保留已有项目约定。
需要我提供的项目事实集中列出，完成后汇报检查结果。
```

首次使用提供仓库地址，是因为本地还没有随包部署的文档。装好后，后续操作优先引用本地 `.agents/docs/` 中的说明。

项目上下文用于告诉 Agent 工程结构、开发约定和入口。工具没有技能选择器时，可以让它直接读取 `.agents/plugins/agent-context-kit/skills/project-context-maintenance/SKILL.md`。

本文默认介绍标准部署：`.agents` 是业务工程内的独立 Git 仓库。若工程已有 `.agents/capability.json`，应按 [Workspace Overlay](../workspace-overlay.md) 解析共享能力包和项目上下文位置，不套用标准部署路径重新安装。

### 2.3 接入这次工作需要的能力

推荐先从[能力目录](capability-catalog.md)找到所需插件和初始化入口，再显式指定。只说明用途不保证模型会主动查找并使用技能；不确定入口时，可以先让 Agent 查目录并给出建议，核对后再执行。下面以 IRIS 开发接入为例：

```text
请读取 .agents/plugins/coding-iris-plugin/skills/coding-iris-init/SKILL.md 并按该技能接入当前工程的 IRIS 后端开发能力。
核对现有启用状态，按真实初始化入口和依赖顺序完成接入。
已有配置保留；缺少信息或存在冲突时列出具体问题。
完成后验证技能入口可读取，并说明还有哪些环境能力未验证。
```

**插件目录存在，不代表已经启用。** Agent 应读取插件声明的初始化入口和依赖，在授权范围内先完成依赖接入，再启用目标能力；更新脚本不会代替初始化，也不会自动启用缺失依赖。

具体接入方式见[使用指南](capability-guide.md)和[插件可用性依赖](../plugin-availability.md)。无需手工修改启用状态来跳过初始化。

### 2.4 按需建立项目资料目录

项目资料需要统一落点时，可以接入目录治理。它将开发指南、业务专题、交付附件和历史资料分别组织到项目 `docs/`，运行状态与恢复资料放到当前项目上下文的 `work/`。

```text
按 .agents/docs/guides/project-knowledge-layout.md 把项目的 docs 骨架搭起来。
先出计划，列出要创建、修改和跳过的准确路径；我确认这一批后再执行。
保留已有资料和人工正文，不搬移旧文件。
```

首次建目录、接管已有导航、搬移旧资料分别按对应计划批准。Agent 应在执行前安排符合要求的备份；计划变化需要重新评审。普通更新只维护已接入目录的受管说明，不能据此搬移旧资料。

详细目录用途、备份及恢复方式见[项目目录治理](project-knowledge-layout.md)。

### 2.5 用一个小任务验证接入结果

选一个范围明确、能观察结果的修改，例如页面查询交互：

```text
使用 iris-frontend-coding，修改当前工程的 [页面文件路径]。
当前问题：[复现步骤与现象]。
预期结果：[修改后的具体行为]。
本轮完成本地实现和适用验证，不提交、不推送、不部署服务器。
结束时说明修改位置、验证方法、结果及尚未验证的部分。
```

请按实际任务替换技能和内容。拿到结果后，核对差异、查看页面或运行对应操作，再判断是否符合预期。只有你确实需要提交或部署时，再明确提出对应请求。

第一次使用的完成标志是：**安装与接入检查有结果、所需入口能被当前工具读取、小任务的行为得到验证**。只有文件存在或生成成功，还不足以证明可用。

## 3. 日常怎么提请求

### 3.1 先指定技能，再给齐任务信息

**目标工程、文件或对象、预期结果、允许的操作范围。** 不知道具体文件时，可以提供页面名称、需求编号、截图或复现步骤，让 Agent 先定位。

| 场景 | 可复制的请求 |
|---|---|
| 查待办 | `使用 bos-demand-query 查询我的开发待办，本轮只读，按需求编号和状态汇总。` |
| 处理需求 | `使用 bos-demand-handle 处理需求 [编号]，先核对当前工程与需求范围，本轮完成分析和本地实施验证；提交、部署及 BOS 写入另行授权。` |
| 排查问题 | `检查 [页面或类] 在 [操作步骤] 后出现的 [现象]，先给证据和原因，本轮不改代码。` |
| 从文档建表单 | `根据 [文档路径] 制作 [CA/CR] 治疗表单，先提取要求并列出待确认字段，确认后再实现和预览；本轮不部署。` |
| 留交接 | `使用 task-handoff，为当前需求保存进展、验证结果、未完成项和下次接续入口。` |

**当前推荐做法：通过宿主的技能选择器显式选中技能，再追加参数和任务说明。** 不同模型主动发现和遵循技能的表现存在差异，不能把“已安装”或“说了用途”当成实际调用的保证。上表中的技能名应尽量通过选择器选中，而不只作为普通文字输入。

例如，选中 [bos-demand-query](../../plugins/bos-plugin/skills/bos-demand-query/SKILL.md) 后追加查询参数：

```text
$bos-demand-query --todo
$bos-demand-query --workload 2026-10-01 2026-10-30
```

这两行是独立示例，按需要选择。`--workload` 必须提供日期或日期范围；仅写 `--workload` 时还需要补充日期。日期、来源范围和其它参数以技能帮助为准。

`$技能名` 表示宿主中的技能引用；纯文本输入是否能绑定技能取决于工具，应核对输入框中是否已选中对应技能。工具没有选择器或入口未被发现时，直接引用实际 `SKILL.md` 文件，并明确要求读取后按其执行。上述内容都是对话请求，不是 PowerShell 命令。

自然语言用于补充目标、对象、预期结果和操作范围。即使已显式指定技能，也应核对 Agent 是否读取了该入口、执行是否遵循对应流程。将来模型的自动发现能力更可靠时，可再简化调用方式；当前手册不以此为前提。

### 3.2 不知道技能怎么用，先加 `--help`

已经找到技能，但不清楚参数、输入要求或操作步骤时，**先在选择器中选中该技能，再追加 `--help`**。例如：

```text
$bos-demand-query --help
```

Agent 应展示该技能的用途、常用参数、输入要求和调用示例。看完帮助，再发出实际执行请求，例如指定日期范围查询工作量。帮助与执行分成两次请求，便于先确认参数和范围。

需要更多细节时，在选中技能后说明“完整帮助”或“全部参数和限制”。工具没有技能选择器时，引用真实 `SKILL.md` 并要求展示帮助；也可以用下面的自然语言请求，但应核对 Agent 是否读取了对应入口：

```text
查看 bos-demand-entry 的用法
查看 iris-deploy 的完整帮助
介绍 coordinator-agent 的用途、输入和调用示例
```

如果连技能名称也不知道，先从[能力目录](capability-catalog.md)或[使用指南](capability-guide.md)选择入口，再查看该技能的帮助。

**`--help` 只展示说明，不执行实际业务操作。** 即使同一请求附带查询条件、`--commit` 或部署对象，也只展示帮助，不进入查询、初始化、提交或部署流程。插件尚未启用、连接配置缺失，不影响阅读帮助。以上约定适用于本仓库自有技能和 Agent；第三方技能按其自身约定。详见[统一帮助](capability-help.md)。

### 3.3 常用能力入口

| 我想做什么 | 入口 |
|---|---|
| 查 BOS 待办 / 工作量 | `bos-demand-query` |
| 处理已有 BOS 需求 | `bos-demand-handle` |
| 从改动生成需求录入文本 | `bos-demand-entry --text` |
| 连续验收、逐号交付 | `demand-acceptance` |
| 明确的前端 / 后端 IRIS 修改 | `iris-frontend-coding` / `iris-backend-coding` |
| 前后端混合、不确定改哪里 | `iris-coding` |
| 解析 Word / PDF / Excel | `extract-doc-ingest` |
| 开发接口、治疗表单、国际化 | 在[使用指南](capability-guide.md)选择对应场景 |
| 按 UI 标注修改 / 核对公司 UI 规范 | `iris-ui` / `imedical-ui-review` |
| 查类方法签名、调用关系 | `iris-mcp-lookup`、`iris-codegraph`、`codegraph-query` |
| 部署 IRIS 文件 | `iris-deploy` |
| 保存交接材料 | `task-handoff` |

多阶段任务允许从已有可信产物接续，无需重复完成前置步骤。Agent 应先核对产物是否适用于当前需求，再继续下一阶段。

### 3.4 四个“通过”不是一回事

| 结果 | 说明 |
|---|---|
| 产物已生成 | 文件或预览已产生，还需要检查内容与行为 |
| 本地验证通过 | 已通过所列本地检查，不代表服务器编译或业务验收通过 |
| 远端已生效 | 已完成对应远端操作与核验，不代表用户业务流程符合预期 |
| 业务验收通过 | 已按约定场景确认符合需求 |

并非每个任务都需要远端操作。听到“已通过”时，核对**通过了哪些检查、证据是什么、还有什么没验证**。图谱和检索结果也是候选证据，关键判断仍应回到源码、配置和实际行为。

## 4. 日常更新与换工具

### 4.1 更新已有能力包

引用本地 `.agents/docs/update-agents.md`，再发出请求：

```text
按这个 runbook 更新当前工程的 .agents。
先 DryRun 给我摘要，没有停止条件就直接 Write，最后 Check。
汇报是否完成、是否执行 Write、需要确认的配置以及未处理的问题。
```

**普通 DryRun 会检查远端，并可能拉取能力包；它不是完全只读。** 如果只想检查现有版本，明确说：

```text
只检查当前已有版本，不访问远端、不修改能力包或项目生成层。
按 runbook 使用 Check 或 DryRun -NoPull，汇报发现的问题。
```

| 模式 | 拉取能力包 | 写项目生成层 |
|---|---|---|
| `Check` | 否 | 否 |
| `DryRun` | 会检查远端，落后时允许 fast-forward | 否，只报告计划 |
| `Write` | 按更新流程处理 | 是 |

严格只读检查不能证明已取得远端最新版。完整状态码、迁移说明和命令统一查[安装更新说明](../update-agents.md)，无需在本手册中逐条记忆。

### 4.2 换一个 AI 开发工具

把实际工具名称、版本和工程位置告诉 Agent：

```text
我现在使用 [工具名称和版本]，请按 .agents/docs/coding-agent-adaptation.md 检查技能发现与项目规则加载。
先 DryRun，列出需要建立或修复的链接及具体路径；我确认后再执行并 Check。
如果工具已原生识别，就保留现状。最后分别汇报技能发现、项目规则加载的验证结果。
```

技能可见和项目规则被加载是两件事，链接创建成功也不代表宿主已经实际读取。必要时刷新工具或开启新会话，再验证入口。

宿主目录和兼容条件统一查[技能适配](../coding-agent-adaptation.md)，以实际版本和加载结果为准；定制客户端不能只按产品名称猜目录。

链接与源目录共享内容，**不要通过删除链接中的技能文件来解除适配**。已有实体目录或错误链接应先核对归属，保留自建技能；修复时只处理获准的链接本身。需要 `CLAUDE.md` / `CODEBUDDY.md` 兼容入口时，按项目规范使用指向 `AGENTS.md` 的 symlink，不复制正文。

## 5. 卡住时怎么处理

先让 Agent 报告：当前对象、实际错误、已做检查、保留的现场，以及需要你决定或操作的最小事项。

| 情况 | 建议处理 |
|---|---|
| 缺少运行环境、登录或权限 | 根据具体缺口安装、登录或授权，完成后让 Agent 复查 |
| `.agents` 是非标准目录 | 先查内容与来源，确认恢复方案，不直接删除重装 |
| `pull-blocked-dirty` | 查明本地改动归属，保留改动，再决定如何处理 |
| 本地领先、分叉或文件冲突 | 核对提交与差异，确定保留方案，不强行拉取 |
| `config-review-required` | 查看具体字段和语义变化后决定 |
| 技能目录链接冲突 | 核对现有目录是否有自建技能，再选择适配方式 |
| 网络或远端访问失败 | 让 Agent 检查具体失败环节；无法访问时说明哪些结果尚未验证 |
| 目录治理报告 `review-required` | 单独核对相关目录或 README；此类问题不阻塞其它更新，不代表目录部分已完成 |

常规、可逆操作可以交给 Agent 完成。首次目录计划、旧资料迁移和存在歧义的冲突，需要你判断；登录、受限环境安装及真实业务验收也可能需要人工操作。

## 6. 操作边界与文件归属

### 6.1 明确本轮允许做什么

本地修改、本地提交、服务器写入、推送、BOS 补录应分别说明授权范围。已明确授权的范围无需反复确认；查看帮助、读取技能或自动发现入口不产生写入授权。

目录计划应展示具体路径，批准针对该份计划；内容变化后重新评审。更新遇到停止条件，应先解决对应问题。

### 6.2 哪些内容属于项目，哪些属于能力包

| 内容 | 维护方式 |
|---|---|
| 能力包受 Git 管理的插件、通用技能、规则、脚本和文档 | 通过能力包版本更新；通用改进回源仓处理 |
| 项目配置、项目规则、项目记忆及任务恢复资料 | 按项目上下文与目录契约维护，保留项目差异 |
| 自动生成的技能或规则入口、README 受管区 | 由对应生成器维护；项目定制放在独立配置或规则中 |
| 业务源码与项目 `docs/` 中的正式资料 | 按业务项目的版本管理和交付约定维护 |

**不能仅凭 `scripts/`、`skills/`、`rules/` 等目录名判断归属。** 这些目录可能同时包含能力包已追踪文件和本地生成文件。`.git/info/exclude` 只影响未追踪文件，不会让已追踪文件变成项目私有文件。

直接修改 `.agents/plugins/` 等受版本管理内容会使能力包工作区变脏，普通更新会报告 `pull-blocked-dirty` 并停止拉取。不要靠强制覆盖解决。标准部署的 `.agents` 是独立仓库，不纳入业务项目提交；也不要将能力包源仓根 `AGENTS.md`、维护者 `memory/` 或展示页复制成业务项目上下文。

### 6.3 连接信息与凭据

凭据不进 Git（包括历史），不写入会进仓的规则、模板、文档或记忆，优先使用系统凭据管理器或环境变量。必须落文件时，使用被忽略的本机实例配置。

IRIS 连接事实按项目约定使用被忽略的 `.mcp.json`；BOS 使用 `BOS_MCP_CONFIG` 指向的仓外私有配置。不要将真实连接信息粘贴到共享手册或能力包中。具体来源与检查方式见[连接信息查看与排查](connection-configuration.md)。

## 7. 项目开发与提交的补充分支

connected、project 且采用按需导出上下文时，待修改文件即使已在本地，也先按[项目开发协议](../../plugins/coding-iris-plugin/references/project-demand-development.md)完成 before-edit 同步；基线有变化先按有效授权提交 export，再开始修改。配置 Check、远端资格、服务器基线分别核实，offline 仍沿离线材料流程。

项目暂时没有需求号时，可显式请求 `$demand-commit --plan --no-id` 预览，获得本地提交授权后用 `$demand-commit --commit --no-id`。该分支只适用于 project，缺编号不会自动采用，standard 仍要求编号；push 和 BOS 写入各核对有效授权。详见[demand-commit](../../plugins/demand-delivery-plugin/skills/demand-commit/SKILL.md)。
