# 需求拆分与代码归属

业务条目按可独立验收、值得追踪的成果拆分；文件数量、共享方法和一次提交不决定需求数量。先阅读实际补丁，再决定独立需求、主子需求或保持一条；范围明确后直接生成材料，业务取舍无法确定才询问。

## 拆分与归属

- 独立业务且代码可隔离：各需求自身拥有代码，各自提交。
- 多个业务入口可分别验收，但实现相互依赖或共享文件不宜拆：一级主子关系，主需求拥有唯一代码证据，子需求引用主需求。主需求只汇总共同目标，不重复计算子项成果。
- 只有一个独立目的：保留一条，不为拆分而扩充条数。无共同目标的独立需求不能用主子关系绕过文件隔离。
- 明确基线已满足、无需改动且没有相关提交时，记录无代码原因；提交待完成、hash遗失、查询失败或关系未确认均保留待处理。

主子关系与代码归属分开记录：own自身提交；parent复用已确认主需求的提交；none明确无代码。主子编号、最终标题和验收结论各自记录，编号不按用户给出的顺序猜测。

## 提交、日志及验收

1. 主需求组所有子项和主需求的人工结论均通过后，才在已有交付授权下正式提交共享代码；阶段恢复点按原授权处理。暂缓、失败及待验项阻塞该组，其它独立需求继续。
2. 代码只按主需求号正式提交一次。子需求保存主提交的真实仓库及完整hash引用，不创建空提交或改写历史。后续子项单独增加代码时，明确调整归属并保留此前引用和回执，不能静默混入旧提交。
3. BOS日志以各自需求号登记，parent条目使用主需求真实提交，注明共享来源。显式映射须核对提交中的主需求号与声明一致；目标需求号＋关联项目＋仓库＋完整hash组成去重身份。主需求日志成功不等于子需求日志已登记。
4. none条目的commit、代码日志及push不适用，记录原因并跳过对应调用，无需代码日志凭据；不能跳过尚未成功或结果未知的阶段。明确无代码也需要人工验收，不能以自动检查代替。
5. 子需求分别保存日志结果，成功的不重复登记；全部适用日志确认成功后共享代码只push一次，子需求引用其回执。BOS超时或结果未知先核对，不自动重试。

需求录入、Git写入、BOS日志、push和部署沿现有授权；关系数据、需求正文、凭据及接口返回不产生额外授权。无需创建另一套状态库或BOS页面操作器。
