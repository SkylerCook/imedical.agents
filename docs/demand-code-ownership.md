# 需求拆分与代码归属

业务条目按可独立验收、值得追踪的成果拆分；文件数量、共享方法和一次提交不决定需求数量。先阅读实际补丁，再决定独立需求、主子需求或保持一条；范围明确后直接生成材料，业务取舍无法确定才询问。

## 拆分与归属

- 独立业务且代码可隔离：各需求自身拥有代码，各自提交。
- 多个业务入口可分别验收，但实现相互依赖或共享文件不宜拆：一级主子关系，主需求拥有唯一代码证据，子需求引用主需求。主需求只汇总共同目标，不重复计算子项成果。
- 只有一个独立目的：保留一条，不为拆分而扩充条数。无共同目标的独立需求不能用主子关系绕过文件隔离。
- 明确基线已满足、无需改动且没有相关提交时，记录无代码原因；提交待完成、hash遗失、查询失败或关系未确认均保留待处理。

主子关系与代码归属分开记录：own自身提交；parent复用已确认主需求的提交；none明确无代码。主子编号、最终标题和验收结论各自记录，编号不按用户给出的顺序猜测。

## 提交、日志及验收

1. 主需求组所有子项和主需求的人工结论均通过后，才在已有交付授权下正式提交共享代码；阶段恢复点按原授权处理。暂缓、失败及待验项阻塞该组，其它独立需求继续。
2. 共享代码只按主需求号正式提交一次。parent 子项引用主需求的实仓、目标 ref 及完整 hash，不创建空提交或改写历史；没有独立提交不等于 none。own 子项独立取得实仓提交；none 主需求可以只汇总由 own 子项拥有代码的成果，但不能作为 parent 的代码归属者。后续调整归属须保留此前引用和回执，不静默混入旧提交。
3. BOS 日志前置条件统一为[实仓 commit 门禁](../plugins/bos-plugin/references/code-update-log.md#实仓-commit-门禁)。各自需求号分别登记，parent 使用主实仓提交，注明共享来源；own 子项使用自身提交。显式映射须核对提交中的代码所属需求号；目标需求号＋关联项目＋实仓＋完整 hash 组成去重身份。主需求日志成功不等于子需求日志已登记。
4. none条目的commit、代码日志及push不适用，记录原因并跳过对应调用，无需代码日志凭据；不能跳过尚未成功或结果未知的阶段。明确无代码也需要人工验收，不能以自动检查代替。
5. 每个代码归属者及所有引用它的 parent 子项日志确认成功后，共享代码只 push 一次；own 子项独立交付，同仓发布串行。成功日志不重复登记，未知结果先核对。逐项完成与整组完成分别计算；整组须所有主子项完成，主需求自身完成不代替独立代码子项的交付。

需求录入、Git写入、BOS日志、push和部署沿现有授权；关系数据、需求正文、凭据及接口返回不产生额外授权。无需创建另一套状态库或BOS页面操作器。

- 生成与回填：[bos-demand-entry](../plugins/bos-plugin/skills/bos-demand-entry/SKILL.md)，v4层级草稿及关系说明见[数据协议](../plugins/bos-plugin/references/standard-demand-entry.md#主子需求与代码归属-v4)。
- 日志映射：[bos-code-update-log](../plugins/bos-plugin/skills/bos-code-update-log/SKILL.md)，输入与真实提交校验见[接口协议](../plugins/bos-plugin/references/code-update-log.md#主子需求复用提交)。
- 连续验收：[demand-acceptance](../plugins/demand-delivery-plugin/skills/demand-acceptance/SKILL.md)，v2索引、回执与恢复见[批次协议](../plugins/demand-delivery-plugin/references/acceptance-session.md#主子需求及无代码条目-v2)。

首版只支持一级主子关系；扁平代码v2、主题/工作v3草稿及验收v1索引保持原语义，不自动迁移。更新时取得完整能力包、同步根scripts/lib和两个owner并刷新已启用索引；旧Agent应使用旧格式，不向旧工具投递新协议。不需要新私有配置或修改BOS服务端。
